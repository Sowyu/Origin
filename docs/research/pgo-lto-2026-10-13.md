# PGO and LTO for Origin release builds on the Mac mini

Date: 2026-10-13. Research only, nothing was built or run. Sources: Zen's workflows from the local `upstream` branch (`git show upstream:<path>`), `configs/`, `scripts/`, surfer in `node_modules/@zen-browser/surfer/dist`, and Firefox 157.0.1 in `engine/`. Times, memory and disk figures for LTO and PGO are my estimates and are marked "unverified".

## Short answer

1. Zen cross-compiles macOS on Linux. Its PGO profile comes from running an instrumented build on a native macOS runner, in three CI stages.
2. On this Mac the same three stages work natively: instrumented build, a roughly 15 minute profiling run in the GUI session, then a build with thin LTO and the profile. Estimated total about 2 to 2.5 hours (unverified).
3. The linker is lld, not Apple's ld, so thin LTO has real job and cache knobs.
4. A profile can be reused for small rebases but should be regenerated for each new Zen or Firefox version (unverified).

## 1. How Zen's CI builds macOS releases

Workflows on `upstream` (`git ls-tree -r --name-only upstream .github`): `build.yml`, `macos-release-build.yml`, `macos-profile-build.yml`, `macos-universal-release-build.yml`, `linux-release-build.yml`, `windows-*`, plus `src/release-build.sh`.

### Cross-compiling on Linux

- `upstream:.github/workflows/macos-release-build.yml:39` runs the macOS build on `blacksmith-8vcpu-ubuntu-2404`, a Linux runner, for `arch: [x86_64, aarch64]` (line 47).
- The build step exports `ZEN_CROSS_COMPILING=1` (`macos-release-build.yml:170`).
- It fetches Mozilla's cross tools with `./mach artifact toolchain --from-build linux64-cctools-port linux64-libdmg linux64-hfsplus` into `~/mac-cross` (`macos-release-build.yml:111-112`).
- `configs/macos/mozconfig:14-27` uses them when `ZEN_CROSS_COMPILING` is set: cctools on PATH, `MKFSHFS`, `DMG_TOOL`, `HFS_TOOL`, and for releases `--enable-linker=ld64` with `MOZ_LD64_KNOWN_GOOD=1` (lines 25-26).
- The two arch builds are joined into a universal app by `macos-universal-release-build.yml` (called from `build.yml:395-404`).

### The three stages

`build.yml:351-393` chains them. They are skipped or used depending on `disable-pgo`.

1. `mac-step-1` (`build.yml:351-364`) calls `macos-release-build.yml` with `generate-pgo: true`. It sets `ZEN_GA_GENERATE_PROFILE=1` (`macos-release-build.yml:171-173`), builds, runs `./mach package` and uploads `zen-macos-pgo-stage1-<arch>.dmg` (`macos-release-build.yml:182-202`).
2. `mac-step-2` (`build.yml:366-376`) calls `macos-profile-build.yml`. It runs on a native macOS runner (`macos-15-intel` or `macos-26`, `macos-profile-build.yml:26`), unpacks the instrumented DMG with `mozbuild.action.unpack_dmg` (lines 81-83), ad-hoc signs it with `codesign --force --deep --sign -` (line 85), downloads the extended corpus (line 95) and runs `build/pgo/profileserver.py --binary <zen> --extended-corpus ./pgo-extended-corpus` with `LLVM_PROFDATA` and `JARLOG_FILE=en-US.log` set (lines 90-96). It uploads `merged.profdata` and `en-US.log` (lines 98-110).
3. `mac-step-3` (`build.yml:378-393`) calls `macos-release-build.yml` again with `generate-pgo: false`. It downloads the artifact to `~/artifact` (`macos-release-build.yml:146-158`) and builds with the profile. The packaging step sets `ZEN_GA_DISABLE_PGO: true` (line 208). Why is unverified.

### Where the PGO profile comes from

- It is generated per release by stage 2 from an instrumented build of the same source. Nothing is committed to the repo. The artifact has `retention-days: 1` (`macos-profile-build.yml:106`).
- Training input is Mozilla's `build/pgo` corpus plus JetStream3 (the "extended corpus"). `scripts/download_pgo_extended_corpus.py:11-55` reads `taskcluster/kinds/fetch/benchmarks.yml` for the URL and SHA-256. The entry is JetStream from GitHub, 194 MB (`engine/taskcluster/kinds/fetch/benchmarks.yml:54-63`).
- `en-US.log` is a jar log for ordering `omni.ja`, passed via `--with-pgo-jarlog` (`configs/macos/mozconfig:46`, used at `engine/toolkit/mozapps/installer/upload-files.mk:7-16`).

### Mozconfig flags

- LTO: `configs/common/mozconfig:74-79`. Unless `ZEN_DISABLE_LTO` is set, it exports `MOZ_LTO=cross,thin` and `--enable-lto=cross,thin`. The macOS file repeats this (`configs/macos/mozconfig:51-60`, x86_64 branch only).
- PGO: `configs/macos/mozconfig:38-48`. `ZEN_GA_DISABLE_PGO` set means no PGO. `ZEN_GA_GENERATE_PROFILE` means `--enable-profile-generate=cross` and `MOZ_AUTOMATION_PACKAGE_GENERATED_SOURCES=0`. Otherwise `--enable-profile-use=cross`, `--with-pgo-profile-path=~/artifact/merged.profdata`, `--with-pgo-jarlog=~/artifact/en-US.log`.
- Native (non-cross) SDK choice: `configs/macos/mozconfig:28-36` picks MacOSX26.5 or 26.4 from the Command Line Tools.
- aarch64: `-mcpu=apple-m1` in CFLAGS and CXXFLAGS (`configs/macos/mozconfig:62-69`).
- Other mozconfig switches that matter: `MOZILLA_OFFICIAL=1` and `AUTOCLOBBER=1` (`configs/common/mozconfig:81-86`).
- The Linux x86_64 config uses full LTO with PGO (`configs/linux/mozconfig:17-20`). macOS stays on thin.

### Scripts that read the env vars

Searched `src`, `configs`, `scripts`, `package.json` and `node_modules/@zen-browser/surfer/dist`. The only readers of `ZEN_RELEASE`, `ZEN_DISABLE_LTO` and `ZEN_GA_DISABLE_PGO` are the mozconfigs above (`configs/common/mozconfig`, `configs/macos/mozconfig`, `configs/linux/mozconfig:11,17`, `configs/windows/mozconfig:41-42`) and `scripts/env.sh:10`. Surfer does not read them. It only templates and concatenates the mozconfig files (`surfer/dist/commands/build.js:50-66`) and appends `./mozconfig` from the working directory if present (lines 52-56). That file is the hook for local overrides.

`.github/workflows/src/release-build.sh:46-54` exports `ZEN_RELEASE=1` and runs `npm run build`. On Linux it also starts Xvfb, but only for non-cross builds (lines 40-45).

## 2. How Firefox does PGO and LTO

### Options (`engine/build/moz.configure/lto-pgo.configure`)

- `--enable-profile-generate[=cross]` (env `MOZ_PROFILE_GENERATE`, lines 9-17). Implies `MOZ_PGO`. Adds `-fprofile-generate` for C and C++ (lines 186 and 165). `cross` adds Rust cross-language PGO (`moz_pgo_rust`, lines 224-250).
- `--enable-profile-use[=cross]` (lines 26-36) with `--with-pgo-profile-path=<abs path to merged.profdata>` (lines 68-101). It requires `LLVM_PROFDATA` and an absolute file path.
- C and C++ use flags are `-fprofile-use=<profdata>` and `-Wno-error=backend-plugin` (lines 199-205).
- On macOS the linker is not a call-graph-sort linker (`pgo_cg_sort` is false for `target.os == "OSX"`, lines 55-58). So an orderfile is made with `llvm-profdata order` (lines 61-65 and 105-122) and passed as `-Wl,-order_file` (line 172). The Mozilla `llvm-profdata` here has the `order` subcommand (checked with `llvm-profdata order --help`).
- `--with-pgo-jarlog` (line 216).
- `--enable-lto[=cross][,thin|full]` (env `MOZ_LTO`, lines 253-262). With no value, clang uses thin on this target (lines 321-336).
- `--enable-profile-generate` turns LTO off: "Disabling LTO because --enable-profile-generate is specified" (line 339). So the instrumented build is never an LTO build.
- Thin LTO flags: `-flto=thin` in cflags and ldflags (lines 369-370). Darwin ldflags add `-Wl,-mllvm,-import-instr-limit=10` and `-import-hot-multiplier=30` (lines 429 and 443). Rust gets `-Clto` thin via `MOZ_LTO_RUST_CROSS` (lines 449-453, `config/makefiles/rust.mk:318-322`).
- Cross-language LTO with Apple's ld64 dies unless `MOZ_LD64_KNOWN_GOOD` is set (lines 351-362). This does not apply to us, see "Linker" below.

### In-tree one-command flow

`engine/build/docs/pgo.md:12-31` says `ac_add_options MOZ_PGO=1` and `./mach build` does three things: an instrumented build in `$topobjdir/instrumented`, a profiling run with `profileserver.py`, and the final `--enable-profile-use` build. `python/mozbuild/mozbuild/build_commands.py:295-380` implements it, including `mach package` of the instrumented build for the jarlog (lines 327-340) and `MOZ_PGO_EXTENDED_CORPUS=1` (lines 304-310). Zen does not use this flow because its mozconfig and CI split the stages. We can also skip it, see risks.

### The profiling run (`engine/build/pgo/profileserver.py`)

- Starts three local servers: the `build/pgo` docroot on a free port (lines 26 and 110-115), Speedometer3 on fixed port 8000 (119-127), and JetStream3 on fixed port 8001 if `--extended-corpus` is given (129-143).
- Makes a temp profile from `testing/profiles` "profileserver" prefs (lines 152-183) and installs the quitter add-on.
- Run 1 opens `quit.html` to initialise the profile (lines 203-225). Run 2 opens `index.html?extendedCorpus=...` with `MOZ_JAR_LOG_FILE` set if `JARLOG_FILE` is set (227-250).
- Sets `LLVM_PROFILE_FILE=<cwd>/default_%p_random_%m.profraw` (lines 190-194). Output goes to the current directory.
- Merges `*.profraw` into `merged.profdata` in the cwd with `llvm-profdata merge` if `LLVM_PROFDATA` is set (lines 287-317).
- `build/pgo/index.html:47-150` is the corpus. About 60 pages of 2 s each (about 2 min), then Speedometer 2, Speedometer3 and WebAudio at 2 min each (lines 123-133), then JetStream3 at 5 min if the extended corpus is on (136-143). That is about 13 to 14 min of wall time plus two launches. The page timers are fixed, so the run length does not depend on how fast the instrumented binary is.
- It opens real windows with `window.open` and uses no headless flag. It exercises Gecko content, layout, JS, graphics and the Cocoa widget. It does not drive Zen's own UI (workspaces, split view). Whether the training covers the paths the energy numbers care about is unverified.

### mach steps

- Build and package: `./mach build`, `./mach package` (surfer wraps these: `surfer build` runs `./mach build` in `engine/`, `build.js:84-100`; `surfer package` runs `./mach package` and copies `obj/dist/*` into `dist/`, `package.js:54-75`).
- Profile: `./mach python build/pgo/profileserver.py ...`, as in `macos-profile-build.yml:96`.

### Linker on this Mac

The current object dir selected lld: `engine/obj-aarch64-apple-darwin/config.status:302,657` has `-fuse-ld=lld`. `toolchain.configure:1980-2005` picks lld by default for clang 15 or later on Darwin. Local clang is 22.1.8 (`~/.mozbuild/clang/bin/clang --version`). So thin LTO runs inside `ld64.lld`, the MOZ_LD64_KNOWN_GOOD check does not apply, and we must not copy Zen's `--enable-linker=ld64` (that line is cross-only, `configs/macos/mozconfig:25-26`).

`ld64.lld --help` lists `--thinlto-jobs=<n>`, `-cache_path_lto <dir>` and `--thinlto-cache-policy`.

## 3. Recipe for this Mac

Every time and size below is unverified unless it quotes `docs/benchmarks.md`. Reference baseline: 1,404 s compile, 14.2 GB peak used, 3 GB swap, 4.9 GB object dir (`docs/benchmarks.md:80-91`).

### Preparation (once)

1. Keep the dev env: `. scripts/env.sh` sets `ZEN_RELEASE=1 ZEN_DISABLE_LTO=1 ZEN_GA_DISABLE_PGO=1` (`scripts/env.sh:10`). Each stage below unsets or overrides these, so give `scripts/build-zen` a stage variable instead of editing `env.sh`. That script builds its environment from `env.sh` (`scripts/build-zen:36-38`), so a wrapper must override after sourcing.
2. Put these in `/Users/mrm/Zen-Origin/mozconfig` (the custom file surfer appends, `build.js:52-56`):

```
# thin LTO link limits, see risks
export LDFLAGS="$LDFLAGS -Wl,--thinlto-jobs=4"
mk_add_options MOZ_MAKE_FLAGS="-j8"
```

   `ZEN_CROSS_COMPILING` stays unset, so the native branch (`configs/macos/mozconfig:28-36`) picks MacOSX26.5.sdk and the cross tools are not used.
3. Download the JetStream corpus (194 MB) with `cd engine && ./mach python ../scripts/download_pgo_extended_corpus.py` (same call as `macos-profile-build.yml:95`). It needs `pyyaml` and `requests` in the mach python, which CI had (unverified here). Skipping it drops the 5 min JetStream item and the `--extended-corpus` flag, with a smaller profile.
4. Free disk: have at least 40 GB free beyond the CandyWrapper floor. Current free is 111 GB.

### Stage A: instrumented build

1. `export ZEN_RELEASE=1 ZEN_GA_DISABLE_PGO= ZEN_DISABLE_LTO=1 ZEN_GA_GENERATE_PROFILE=1`. Unset (not empty-string) `ZEN_GA_DISABLE_PGO` and `SURFER_COMPAT`, because the mozconfig uses `test "$X"` which treats empty as unset, so either works. Leaving `ZEN_DISABLE_LTO=1` is harmless: LTO is forced off here (`lto-pgo.configure:339`).
2. `scripts/detach build-gen scripts/build-zen build package`. Needs a clean configure. `AUTOCLOBBER=1` (`configs/common/mozconfig:85-86`) clobbers the object dir when the mozconfig changes, which means a full rebuild of the existing 4.9 GB dir.
3. Result: `engine/obj-aarch64-apple-darwin/dist/<app>.app` plus the DMG in `dist/`.
4. Estimate: 30 to 40 min, 14 to 15 GB peak with swap, object dir 6 to 8 GB. Instrumentation adds code size and compile time. The package step is about 2 min.

### Stage B: profiling run (needs the GUI session)

- Yes, it needs a window server session. The upstream job runs on a real macOS runner with no headless setting (`macos-profile-build.yml:87-96`), and the corpus pages call `window.open`. Headless Gecko on macOS takes different widget and compositor code paths, so a headless profile would miss them (unverified).
- Run it in the user's session, detached, with output to a log:

```
scripts/detach pgo-run sudo launchctl asuser 502 sudo -u mrm /bin/zsh -c \
 '. /Users/mrm/Zen-Origin/scripts/env.sh; cd /Users/mrm/Zen-Origin/engine; \
  export LLVM_PROFDATA=$HOME/.mozbuild/clang/bin/llvm-profdata JARLOG_FILE=en-US.log; \
  ./mach python build/pgo/profileserver.py \
    --binary <objdir>/dist/<App>.app/Contents/MacOS/<binName> \
    --extended-corpus ./pgo-extended-corpus'
```

- The Mac harness uses the same `launchctl asuser 502 sudo -u mrm` form (`CLAUDE.md`, machine facts).
- Copy the products where the stage C mozconfig expects them: `mkdir -p ~/artifact && cp merged.profdata en-US.log ~/artifact/` (`configs/macos/mozconfig:45-46`). Both land in `engine/` (the cwd).
- Do not run the app bundle unsigned if Gatekeeper complains. CI ad-hoc signs the extracted app first (`macos-profile-build.yml:85`). Local builds run from the object dir are not quarantined, so this may be unneeded (unverified).
- Time: about 15 min of corpus plus merge. The window shows pages for the whole run, so no other GUI work or energy batch on the same screen (the harness waits for a quiet machine; a profiling run will mark any concurrent run noisy).
- Disk: `.profraw` files go to `engine/`. Size for a Firefox profile run is hundreds of MB to a few GB (unverified). `merged.profdata` is typically tens to a few hundred MB (unverified).
- Fixed ports 8000 and 8001 must be free. The perf fixture server uses 8765 by default (`scripts/perf/serve:112`), so no clash.
- Memory: a normal browser session plus instrumentation, under 3 GB (unverified).

### Stage C: final build with thin LTO and the profile

1. `export ZEN_RELEASE=1; unset ZEN_DISABLE_LTO ZEN_GA_DISABLE_PGO ZEN_GA_GENERATE_PROFILE`. Resulting options come from the existing mozconfig: `--enable-lto=cross,thin` (`configs/common/mozconfig:77-78`), `--enable-profile-use=cross`, `--with-pgo-profile-path=$HOME/artifact/merged.profdata`, `--with-pgo-jarlog=$HOME/artifact/en-US.log` (`configs/macos/mozconfig:44-46`), plus the custom `LDFLAGS`.
2. `scripts/detach build-final scripts/build-zen build package`.
3. Estimates, all unverified:
   - Compile: 1.3 to 1.6 times the non-LTO build because profile-use compile does more work and thin LTO emits bitcode, so about 35 to 40 min.
   - Rust: cross-language LTO makes Rust crates emit bitcode that the final link consumes (`rust.mk:318-322`), so more memory in the Rust phase.
   - Link of libxul with thin LTO: the whole backend runs in the link. On 10 cores with the default job count I would expect 15 to 40 min. With `--thinlto-jobs=4` expect the longer end.
   - Package: about 2 min.
   - Total about 1 to 1.5 hours.
4. Memory: unverified. The link holds the combined index for all bitcode plus up to N concurrent backend jobs, each commonly 0.5 to 1.5 GB. Peak for the link alone I would guess 6 to 12 GB. The compile phase before it already peaked at 14.2 GB without LTO, so keep `-j` at 8 (or lower the swap pressure).
5. Disk: bitcode objects are bigger than machine-code objects. Estimate 8 to 11 GB for the object dir, so the whole tree needs about 20 to 24 GB. Delete the stage A object dir content when stage C reconfigures (AUTOCLOBBER does this).

### Keeping the libxul link under 16 GB

- Use thin LTO only. Never `full`. Full LTO uses one giant module and is the usual out-of-memory case.
- Add `-Wl,--thinlto-jobs=4` to `LDFLAGS` (`ld64.lld --help` confirms the flag). The default is the lld thread count (all 10 cores).
- Add `-Wl,-cache_path_lto,$HOME/.cache/origin-lto` so a retry or a small rebuild reuses backend results.
- Run no other builds, no `report`, no browsers during the link.
- Watch it with `scripts/build-zen`'s `mem.tsv` (5 s samples, `build-zen:79-86`) and lower to `--thinlto-jobs=2` if swap exceeds 5 GB.
- Rust crates: `-Clto` thin per crate happens in cargo parallel jobs; if needed lower `-j` (cargo uses the same jobserver as make, unverified).
- If the link still dies, retest with `MOZ_LTO=thin` instead of `cross,thin`, which drops Rust bitcode from the link (loses cross-language inlining, so less gain).

## 4. Risks

1. First run is the test: nobody has linked libxul with LTO on this exact toolchain here. Failure modes are out-of-memory kills and swap thrash (shared machine, CandyWrapper agents also use RAM). Unverified for time and memory.
2. The mozconfig reads `~/artifact/...` with a hard-coded path (`configs/macos/mozconfig:45-46`). If the file is missing, configure fails with "must be a file" (`lto-pgo.configure:94-95`). Fine, but easy to hit.
3. `AUTOCLOBBER=1` plus a changed mozconfig means each stage is a full rebuild. Stage A and stage C do not share objects.
4. Zen's upstream skipped `ZEN_GA_DISABLE_PGO` only on the package step (`macos-release-build.yml:208`). We package right after the build in the same env. If `mach package` re-runs configure, the missing profile path could break it. Unverified. Fallback: export `ZEN_GA_DISABLE_PGO=1` only for `package`.
5. Cross-language LTO needs the clang and rustc LLVM versions to match closely. Local clang is 22.1.8 and rustc 1.95.0 uses LLVM 22.1.2 (checked with `rustc -vV`). Rust's LLVM is older than clang's, which is the safe direction (unverified).
6. The profile run is Mozilla's synthetic corpus on the Zen app. It does not touch Zen workspaces, split view or tab animation. The 36% energy gain seen in official Zen builds used the same corpus (`macos-profile-build.yml:95-96`), so a similar gain is plausible, but our branding or pref changes could alter coverage (unverified).
7. The first-run page of the app may block the profile run (welcome tab, update checks, Zen onboarding). CI worked with the same code path, but Origin has different branding and removed features (`docs/cuts.md`). Check the log after the first minute: there should be `.profraw` files in `engine/`. Fixed ports and a fresh temp profile remove most surprises.
8. Gatekeeper: if the instrumented app refuses to start, ad-hoc sign it as CI does (`codesign --force --deep --sign -`).
9. Instrumented binaries write profile data on exit. If the app crashes, files may be incomplete. `profileserver.py` exits non-zero on crash (lines 255-263) and CI uploads nothing then.
10. Spotlight and load: keep `engine/` as the `.noindex` symlink target, as now.

### Can a profile be reused across weekly rebases?

Not as a rule. The profile is matched per function by a control-flow hash. When Zen patches or the Firefox base change a function, LLVM drops its profile data, and the flags that tolerate mismatches are already set (`-Wno-error=backend-plugin`, `-Wcoverage-mismatch` for gcc only; `lto-pgo.configure:155 and 199-205`). A weekly rebase that only touches Zen JS, CSS and prefs leaves C++ unchanged, so the old `merged.profdata` should still apply. A Firefox base bump (such as 157 to 158) or a clang bump changes many functions, so regenerate. Both claims are unverified here. Check with a warning count: build with `-Wprofile-instr-missing` / look for "profile data may be malformed or out of date" and compare coverage mismatch counts (unverified flag names).

Upstream Zen never reuses a profile. It regenerates in every release (`build.yml:351-393`), and its artifact lives one day (`macos-profile-build.yml:106`).

Cost to regenerate: stage A plus B is about 45 to 55 min of the 2 to 2.5 h total, so the practical weekly loop is: keep the stage C object dir warm, reuse the last profile, and run the full three stages only on version bumps and releases.
