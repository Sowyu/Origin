# Widevine DRM and Firefox Sync for Zen Origin on macOS

Date: 2026-10-12. Source tree: Firefox 157.0.1 in /Users/mrm/Zen-Origin/engine (still unpacking when I read it, so taskcluster and build/ were partial). Inspected DMGs: zen-1.23.2b.macos-universal.dmg and firefox-157.0.1.dmg, read-only, now detached.

Labels used below: FACT means I read it in a file or a page. INFERENCE means I reasoned from facts. UNVERIFIED means I could not confirm it.

## Short answers

1. Firefox does not bundle Widevine. It downloads Google's CDM at runtime, using a Mozilla update-XML call first and a Google component-updater call second, and stores it in the profile. The CDM then checks the host app's files against `.sig` files (Verified Media Path).
2. Official Firefox for Mac ships five `.sig` files, each 1449 bytes. The official Zen DMG ships none. Mozilla produces them through its signing pipeline with a Google-issued Widevine certificate that Mozilla holds. Zen's own FAQ says Netflix and Spotify do not play in Zen on Windows and macOS because Zen has no Widevine license.
3. Netflix and Spotify on an unsigned Gecko build on macOS: most likely they fail or play at low quality. I found no test report for the exact case, so the exact failure is UNVERIFIED. Your test steps below settle it on your own build.
4. Waterfox says its Mac builds now play DRM. Floorp, Zen and Mullvad do not. LibreWolf turns DRM off by default and has no Mac notarization. I found no fork that documents how it got VMP signing.
5. A small fork can get signing only through Google's Widevine 3PL route, or through castLabs with a commercial audit. castLabs EVS is free only for official castLabs Electron builds. Developer ID is not mentioned in either route, but I could not confirm it either way.
6. Firefox Sync works in a fork without any client id change. Zen uses Firefox's client id as is. A differently branded or unsigned build does not break sign-in by itself. Mozilla's rules for third-party clients are about honest identity and trademarks, and I found no rule that blocks forks.

## 1. How Widevine reaches a Firefox build on macOS

FACTS from the 157.0.1 source:

- The build flag `--enable-eme=widevine` defines `MOZ_WIDEVINE_EME` (engine/toolkit/moz.configure:926-934). Zen sets it in /Users/mrm/Zen-Origin/configs/macos/mozconfig:9.
- Pref `media.gmp-manager.url` is `https://aus5.mozilla.org/update/3/GMP/%VERSION%/%BUILD_ID%/%BUILD_TARGET%/%LOCALE%/%CHANNEL%/%OS_VERSION%/%DISTRIBUTION%/%DISTRIBUTION_VERSION%/update.xml` (engine/modules/libpref/init/all.js:3486).
- The browser sends no body and no cookies. It sends only those URL fields, filled in by engine/toolkit/modules/UpdateUtils.sys.mjs.
- Zen patches `VERSION` to send `AppConstants.ZEN_FIREFOX_VERSION` (src/toolkit/modules/UpdateUtils-sys-mjs.patch). `DISTRIBUTION` will carry your distribution id (`app.zen-browser` in Zen's mozconfig, `--with-distribution-id`).
- Second path: `media.gmp-manager.chromium-update-url` is `https://update.googleapis.com/service/update2/crx?response=redirect&x=id%3D%GUID%%26uc&acceptformat=crx3&updaterversion=999` (engine/browser/app/profile/firefox.js:2527). The Widevine L3 GUID is `oimompecagnajdejgnnjijobebaeigek` (firefox.js:2530). `GMPUtils._getChromiumUpdateParameters` adds `&os=mac&arch=arm64&os_arch=arm64` (engine/toolkit/modules/GMPUtils.sys.mjs:108-142). GMPInstallManager follows the redirect with an anonymous request and downloads the CRX3 from Google (GMPInstallManager.sys.mjs:61-80, 391-480).
- Fallback: `media.gmp-manager.allowLocalSources` is true (all.js:3482). The bundled list engine/toolkit/content/gmp-sources/widevinecdm.json pins Widevine 4.10.3050.0 with Google CDN URLs (edgedl.me.gvt1.com and www.google.com/dl) and SHA-512 hashes. The mac arm64 file is 20,189,918 bytes.
- Related prefs: `media.gmp-widevinecdm.enabled`, `.visible`, `.allow-chromium-update`, `.force-chromium-update` (firefox.js:2526-2545). There is also an L1 variant, `media.gmp-widevinecdm-l1.*`, which is for Windows only as far as I can tell (UNVERIFIED for mac).
- Storage: the CDM goes in the profile as `gmp-widevinecdm/<version>/` with `libwidevinecdm.dylib` and a manifest. Installed version and ABI sit in prefs `media.gmp-widevinecdm.version` and `.abi` (GMPProvider.sys.mjs). The exact on-disk path is INFERENCE from how GMPInstallManager extracts, not something I opened. Check it on your build.
- The CDM runs inside a GMP child process, the "Firefox Media Plugin Helper" app on macOS (present in both DMGs under Contents/MacOS/media-plugin-helper.app).

What the CDM checks about the host (FACT from source plus INFERENCE about the CDM, which is closed source):

- `GMPChild::MakeCDMHostVerificationPaths` (engine/dom/media/gmp/GMPChild.cpp:399-500) collects the plugin dylib, the GMP process binary, the app binary named `MOZ_APP_NAME`, and libxul (`XUL`), each paired with a `.sig` file.
- On macOS the `.sig` files sit in `Contents/Resources` of the bundle that owns the binary (GMPChild.cpp:405-407).
- `ChromiumCDMAdapter::GMPInit` calls the CDM export `VerifyCdmHost_0` with those file handles (ChromiumCDMAdapter.cpp:88-100).
- The call exists only under `#ifdef MOZILLA_OFFICIAL`. Zen's release mozconfig sets `MOZILLA_OFFICIAL=1` in the `ZEN_RELEASE` block (configs/common/mozconfig:81-83). A local non-release build may skip the call, which changes what you see.
- Firefox ignores the result in release builds. It only runs `MOZ_DIAGNOSTIC_ASSERT(result)`, which is fatal only on Nightly and debug builds (INFERENCE from the macro's usual meaning).
- INFERENCE: the real enforcement happens inside the CDM and Google's license server. The CDM reports its host-verification state, and the license server decides what it will give out.
- The CDM also looks at the code signature of the process and the macOS sandbox. UNVERIFIED which checks are active on Apple Silicon.

## 2. VMP on macOS

FACTS from the DMGs (mounted at /tmp/dmg-ff and /tmp/dmg-zen, now detached):

Official Firefox 157.0.1 has these `.sig` files, all 1449 bytes:

- Firefox.app/Contents/Resources/XUL.sig
- Firefox.app/Contents/Resources/firefox.sig
- Firefox.app/Contents/MacOS/plugin-container.app/Contents/Resources/plugin-container.sig
- Firefox.app/Contents/MacOS/media-plugin-helper.app/Contents/Resources/Firefox Media Plugin Helper.sig
- Firefox.app/Contents/Resources/gmp-clearkey/0.1/libclearkey.dylib.sig

The XUL and firefox files have different contents (SHA-1 03eebc99... and ed91b876...). Each one signs a different binary.

Official Zen 1.23.2b has no `.sig` file anywhere in Zen.app. `find Zen.app -name "*.sig*"` returned nothing. Its Contents/Resources holds only XUL-less resources (application.ini, omni.ja, gmp-clearkey and similar). Its main binary is `zen`, so even with sigs the file would need to be `zen.sig`, because GMPChild builds the name from `MOZ_APP_NAME` (GMPChild.cpp:367-369, 493).

What the Firefox sig contains, from `strings` on XUL.sig (FACT for the names, INFERENCE for the dates): a certificate chain naming Google, Widevine, "widevine-codesign-root-ca", and Mozilla "Release Engineering" with release@mozilla.com. The validity strings read 170727225147Z to 270725225147Z, which I read as 2017-07-27 to 2027-07-25. If right, the signing certificate expires in July 2027. That matters for planning if you ever get one.

What produces them (FACT from engine/taskcluster):

- Mozilla's signing task asks for format `gcp_prod_autograph_widevine` on the macOS app and on Windows and Linux packages (taskcluster/gecko_taskgraph/util/signed_artifacts.py:81, 109, 122).
- taskcluster/docs/signing.md:114-115 says "We sign specific files inside the package and rebuild the `precomplete` file."
- Mozilla's Autograph service holds the key, and its signingscript does the signing. Partner repacks skip this format (signed_artifacts.py:161-169).
- Because `precomplete` is rebuilt, a fork that adds sigs by hand must keep its update manifest consistent.
- On macOS the order matters: VMP signing first, Apple code signing last. That is castLabs' rule for Electron (castlabs EVS wiki). It matches Mozilla signing macapp then widevine in the format list, but I did not check the exact order Mozilla uses (UNVERIFIED).

What happens without the sigs on macOS: UNVERIFIED. The evidence I have:

- Zen's FAQ (https://docs.zen-browser.app/faq) says Zen "currently lacks DRM support, as it does not yet have a Widevine license", names Netflix and Spotify, says it affects only Windows and macOS, and says the team is waiting on Google.
- Floorp says the same (see section 3).
- Mozilla bug 2067309 (https://bugzilla.mozilla.org/show_bug.cgi?id=2067309): tests with the real Widevine plugin fail in CI on macOS because the plugin "doesn't trust the environment and/or the build", and a signed build might fix it. This is the closest official statement that an unsigned Mac build is distrusted.
- Zen on Windows (https://github.com/zen-browser/desktop/issues/12594) shows UI3012 and E100 on Netflix. A contributor said "DRM is not available in Zen right now". That is Windows and a different path (PlayReady, MF media engine), so it only hints at the Mac behaviour.
- Netflix's own page (https://help.netflix.com/en/node/23742) says Firefox on Windows and Mac is capped at 1080p, needs Firefox 129 or newer, and needs macOS 10.15.5 or newer. Whether an unsigned build gets lower resolution (L3 at 540p or 720p) or no playback is UNVERIFIED.
- Netflix error codes: I found no report tying M7701, M7121 or M7361 to Gecko forks on Mac. Older Firefox reports use F7121-3078 and F7701-1003 (Mozilla support thread 1389788, bug 1276057). A Vivaldi thread ties M7121-1331 to a broken Mac Widevine signature (https://forum.vivaldi.net/post/668927). Treat those as hints on what to look for, not as a map.
- Spotify web player: no source found. Spotify web uses Widevine for all playback, so INFERENCE is that it errors with "Playback of protected content is not enabled" or similar when the CDM is missing or refuses. UNVERIFIED.
- Public test pages (no source needed for the existence of them): Shaka Player demo (https://shaka-player-demo.appspot.com/), Bitmovin DRM demo, castLabs and Axinom players. I did not run them.

## 3. What other forks do on macOS

- Zen: no Widevine license, no sigs in the DMG (checked). Netflix and Spotify are listed as unsupported on Windows and macOS (https://docs.zen-browser.app/faq). A search snippet also quoted a cost of "at least $5,000" and the team calling it financially unwise, but I did not find that in the page text I fetched, so treat the number as UNVERIFIED.
- Floorp: states it has no Widevine license, says it will not fix this, names Netflix as affected (https://docs.floorp.app/en/issues/drm/ as reported by a search result; my direct fetch of /docs/issue-tracker/drm was not retrievable). Cost "at least $5,000" is from the same snippet. UNVERIFIED in detail.
- Waterfox: its DRM help page (https://www.waterfox.com/support/drm-content/) says it supports Widevine, downloads it on demand, runs it sandboxed, and lists macOS 10.11 and later. Release notes G5.1.7 said macOS DRM was not yet supported. A search result quoted G6.0.20 as saying DRM now works on macOS with Netflix, Prime Video and Disney+, and G6.0 Beta 3 as calling it experimental. I could not open those notes (404 on the .com mirror, redirect on .net). How Waterfox got a working Mac build, and whether it has VMP signing, is UNVERIFIED. This is the one fork worth contacting.
- LibreWolf: DRM is off by default and is enabled under Settings > General > Digital Rights Management (https://librewolf.net/docs/faq/). The FAQ does not say Widevine. It says LibreWolf does not notarize its macOS build. No Netflix or VMP claim.
- Mullvad Browser: DRM and EME are off by design (forum posts quoting Mullvad; no official page fetched). UNVERIFIED but consistent.
- None of them documents Google VMP signing. Only Waterfox claims Mac DRM works, and I found no write-up of how.

## 4. What VMP signing takes for a small open source fork

FACTS:

- Google says a license agreement is required to use Widevine products, that there is no fee for the Cloud License Service, and that integration questions go through Widevine support (https://developers.google.com/widevine/drm/overview). It does not describe the browser or VMP route.
- widevine.com/contact lists "Widevine 3PL" (third-party licensee) and a partner training program (CWIP), with no terms or prices on the page.
- castLabs EVS (https://github.com/castlabs/electron-releases/wiki/EVS) is free, needs an account, a Python client (`castlabs-evs`), and tokens that expire roughly monthly. It signs macOS and Windows, not Linux. It is for official castLabs "Electron for Content Security" builds. For a custom build it says "Once an implementation is audited commercial 3PL access to EVS is granted", contact 3pl@castlabs.com. It gives no price. The page says it signs the `.app` inside the Electron layout and, for custom builds, an executable with a separate signature file placed where your VMP code looks. That last mode could in principle match Gecko's `.sig` layout, but nobody has documented it, so it is UNVERIFIED.
- EVS wiki and PyPI listing say nothing about Apple Developer ID or notarization. The only macOS rule stated is: VMP-sign first, then Apple code sign.

INFERENCE and unknowns:

- Realistic path: apply for Widevine 3PL through Google, or buy castLabs commercial certification. Both want an audited, shipped product with a company behind it. Cost and timeline for a hobby fork: UNVERIFIED. Floorp and Zen both say they could not get or afford it, which hints that it is hard.
- Without a Developer ID: the `.sig` is a separate signature, not an Apple one, so VMP signing itself probably does not need Developer ID. But the Widevine CDM and Apple's library validation interact with your code signature (Vivaldi's notarization trouble in 2019 and 2020, forum.vivaldi.net/post/668927). An Apple Development certificate may make the CDM or sandbox refuse the build. UNVERIFIED. Test it (steps below).
- Mozilla will not sign your build. Their key is Mozilla's, and their pipeline deliberately skips partner builds (`_strip_widevine_for_partners`). Do not copy Firefox's `.sig` files into your app: they sign Firefox's hashes, would not match your binaries, and reusing Mozilla's signature would be misuse of their credentials.

## 5. Firefox Sync in forks

FACTS from engine/browser/app/profile/firefox.js:2462-2492 and services/fxaccounts:

- Prefs that turn it on: `identity.fxaccounts.enabled` true. Servers: `identity.fxaccounts.remote.root` https://accounts.firefox.com/, `.remote.profile.uri` https://profile.accounts.firefox.com/v1, `.remote.oauth.uri` https://oauth.accounts.firefox.com/v1, `.auth.uri` https://api.accounts.firefox.com/v1 (all.js:3863), `.remote.pairing.uri` wss://channelserver.services.mozilla.com, `identity.sync.tokenserver.uri` https://token.services.mozilla.com/1.0/sync/1.5. Self-host override: `identity.fxaccounts.autoconfig.uri`.
- Client id: `FX_OAUTH_CLIENT_ID = "5882386c6d801776"` is hard-coded in services/fxaccounts/FxAccountsCommon.sys.mjs:94 and used for every desktop FxA OAuth request. It is picked by `MOZ_APP_NAME == "thunderbird"` only. No pref changes it. The related Monitor, Relay and VPN ids are on lines 123-125.
- Sign-in runs through the web channel from the remote root page, so the check is on accounts.firefox.com, not in the browser binary. No signature or `MOZILLA_OFFICIAL` check appears in services/fxaccounts or services/sync/modules (my grep found none).
- Zen: I found no patch to FxAccountsCommon or any `identity.*` pref in /Users/mrm/Zen-Origin/src or /Users/mrm/Zen-Origin/prefs. Zen only adds a custom sync engine (`services.sync.engine.spaces`, prefs/zen/sync.yaml, src/zen/sync/ZenSpacesSync*.mjs) and pref-sync entries for its own prefs. Zen's FAQ says users sign in with a Mozilla account for sync.
- The server may store the user agent string of the device; your branding shows up in the device list (FxAccountsDevice.sys.mjs). Harmless.

Terms (FACT unless noted):

- Mozilla Accounts Terms (https://www.mozilla.org/about/legal/terms/services/, last updated 2026-09-16) say Sync needs a Mozilla account. They say nothing about forks, unofficial builds or API access.
- Mozilla's Sync API terms for third-party clients (https://mozilla-services-docs.readthedocs.io/en/latest/tos.html, possibly outdated): store data only in encrypted form, publish a privacy policy, do not hide the client's identity, do not imply Mozilla endorsed it, no trademark license, and a Sync-like service must be non-confusing about who runs it. A rebranded fork with its own name and honest about-page fits this.
- Whether Mozilla can revoke the shared client id for forks: UNVERIFIED. Nothing I found says they do. Registering your own OAuth client with Mozilla needs Mozilla's cooperation and I found no public process.

Does unsigned or differently branded break it: INFERENCE no. Sign-in has no code-signing dependency in the source I read. Risk points to test: the user agent and `app.update`/distribution strings, any rate limiting, and keychain access under an Apple Development signature (Sync stores the login in the OS credential store, so a changed signing identity can show a keychain prompt).

## Test steps for your own build

Setup: use a fresh profile (`zen-origin -P` to create one). Put the app outside /Applications if you like. Run it from Terminal so logs print.

Log it:

```
MOZ_LOG="GMP:5,EME:5,EMEV:4,GMPLibrary:5,MediaDecoder:3,sync:5" MOZ_LOG_FILE=/tmp/zo-gmp.log /path/to/ZenOrigin.app/Contents/MacOS/zen -P test-drm
```

`GMP`, `EME`, `EMEV` and `GMPLibrary` are real module names in the source (GMPLog.h, EMEUtils.cpp). The last `sync` module name is a guess, UNVERIFIED. Also set `media.gmp.log.dump` and `media.gmp.log.level` in about:config only if the MOZ_LOG output is empty (UNVERIFIED that those prefs exist; check about:config search for `media.gmp`).

1. Confirm the bundle. Run `ls "<app>/Contents/Resources"` and `find "<app>" -name "*.sig"`. Expected: no `.sig` files. This is your baseline. Run `codesign -dv --verbose=4 "<app>"` and note the TeamIdentifier and flags (runtime or not).
2. about:preferences, section Digital Rights Management (DRM) Content: tick "Play DRM-controlled content". Expected: a Widevine entry downloads. Watch `/tmp/zo-gmp.log` for the aus5 call and the googleapis redirect.
3. about:addons > Plugins. Expected: "Widevine Content Decryption Module provided by Google Inc." with version 4.10.x and status enabled. If it says "Installing" for minutes, check network to update.googleapis.com and aus5.mozilla.org.
4. about:config, check these: `media.eme.enabled` true, `media.gmp-widevinecdm.enabled` true, `media.gmp-widevinecdm.visible` true, `media.gmp-widevinecdm.version` (non-empty), `media.gmp-widevinecdm.abi`, `media.gmp-manager.url`, `media.gmp-manager.chromium-update-url`, `media.gmp-manager.lastCheck`, `media.gmp-provider.enabled` true, `media.gmp-manager.updateEnabled` true. Also `privacy.resistFingerprinting` false, because Zen reports of Netflix logouts mention fingerprinting protection.
5. about:support, Media section: look at "Media Capabilities" and "Codec Support Information", and at the "Content Decryption Modules" or "GMP plugins" listing if present (name varies by version). Expected: Widevine listed with version. Also read Graphics > "Media Hardware Decoding / HW DRM" lines. Write down what you see; this is a diff for later.
6. Shaka Player demo (https://shaka-player-demo.appspot.com/, pick a Widevine asset such as "Angel One (multicodec, Widevine)"). Expected if VMP is accepted: plays. If not: a console error about license request denied or CDM failure. Open the Web Console and save the error text. Run it on the official Firefox 157.0.1 too, as the control.
7. Bitmovin DRM demo and a castLabs or Axinom test player. Same check. Their stats overlay shows the Widevine robustness level (L3 expected, SW_SECURE_CRYPTO or SW_SECURE_DECODE). Note the max resolution offered.
8. Netflix. Sign in, play a title, press Ctrl+Option+Shift+D (or Ctrl+Alt+Shift+D) for the stats overlay, and note video resolution and the DRM state. Expected on official Firefox: up to 1080p per Netflix. If your build fails, record the error code (F7121-3078, F7701-1003, M7121-1331, M7701-1003, M7361-1253 or others) and the log lines.
9. Spotify web player (https://open.spotify.com): sign in and play a track. Expected: plays. Failure text goes in the notes.
10. Check the log. Search /tmp/zo-gmp.log for "VerifyCdmHost_0 returned", "Verification failed", "ChromiumCDMAdapter", "GMPInit", "CDM", "license", "load" and for crash lines. If you see `VerifyCdmHost_0 returned 0`, the CDM saw missing sigs. If there is no such line, your build does not define `MOZILLA_OFFICIAL`, so the host check never ran and you tested a different thing than a release build. Rebuild with `ZEN_RELEASE` set to match.
11. Try an Apple Development vs. ad-hoc signature. Run `codesign -dv --entitlements - "<app>"` and check entitlements for `com.apple.security.cs.disable-library-validation` and `allow-unsigned-executable-memory`. A hardened-runtime build that blocks loading the Google-signed `libwidevinecdm.dylib` shows a dyld or "code signature invalid" line in the log or Console.app. This tests the question of whether a missing Developer ID breaks the CDM.
12. Compare control runs: repeat steps 6, 8, 9 in the official Firefox 157.0.1 and the official Zen 1.23.2b (use fresh profiles, do not install into /Applications). Zen 1.23.2b should match your unsigned result and Firefox should differ. That pins the difference on the sigs and not on the network.

Sync test:

13. In your build open about:preferences#sync and sign in with a test Mozilla account (or create one). Expected: the sign-in page loads from accounts.firefox.com, you return signed in, the first sync starts.
14. about:config: confirm `identity.fxaccounts.enabled` true, `identity.fxaccounts.remote.root`, `identity.sync.tokenserver.uri`, `services.sync.username`, `services.sync.lastSync`, `services.sync.engine.*` and (if you kept Zen's engine) `services.sync.engine.spaces`.
15. Add a bookmark here and watch it appear in official Firefox signed into the same account within a few minutes. Then change something in Firefox and watch it arrive. Send Tab between the two.
16. about:sync-log: open the newest log and check for `401`, `UNKNOWN_CLIENT_ID`, `invalid-client`, or token server errors. Also run `about:support` > "Sync" / Accounts rows, and `MOZ_LOG="sync:5,FxAccounts:5"` for details (module names UNVERIFIED). Check the macOS keychain prompt: sign out and in once to see whether your Apple Development signature causes a repeat Keychain dialog.
17. Quit and relaunch; confirm you stay signed in and the device list in accounts.firefox.com/settings shows your device name with your branding.
