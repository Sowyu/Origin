## Q1. Gecko power features on macOS (PARTIAL, more appended below)

### Compositor / video
- gfx.webrender.compositor = true on Windows, macOS, GTK (SPL ~L8546). Mirror once (restart). On macOS this is the CoreAnimation native compositor. Force pref: gfx.webrender.compositor.force-enabled=false. Other: gfx.webrender.compositor.max_update_rects=1, gfx.webrender.compositor.surface-pool-size=25.
- gfx.webrender.layer-compositor = false on macOS (true only on Windows/GTK) (SPL ~L8550). So macOS has NOT moved to the newer "layer compositor"; still the older native-compositor path.
- gfx.webrender.max-partial-present-rects = 0 on macOS (1 on Win/Android/GTK) (SPL ~L8608). Partial present off on mac; damage handled via CoreAnimation layers instead.
- gfx.core-animation.specialize-video = true only on aarch64 macOS, false on Intel (SPL ~L7709; comment: "specialized video-only layers for video content in fullscreen windows. Consistently works well on Apple Silicon, some issues remain on Intel"). I.e. direct-to-CALayer video overlay is fullscreen-only by this pref's own comment.
- gfx.core-animation.tint-opaque=false (debug tint). gfx.core-animation.low-power-telemetry-frames=600 (a telemetry hook exists for "low power" = frames drawn in the CoreAnimation low-power mode; see Q2).
- Nightly-only debug: gfx.core-animation.specialize-video.{spoof-timing,check-color-space,log}.
- gfx.compositor.gpu-migration=true (mac) GL context follows the GPU OS uses (irrelevant on Apple Silicon, single GPU).
- Related bugs: 1747999 (subtitle brightness flash with video overlay, colorspace), https://bugzilla.mozilla.org/show_bug.cgi?id=1747999 ; Core Animation history: https://bugzilla.mozilla.org/show_bug.cgi?id=1620578 and 1727198 (not yet read).

- media.av1.enabled=true; media.av1.use-dav1d=true (software dav1d is the default decoder; HW AV1 on M3+ via VideoToolbox: bug 1871796 "AV1 Hardware Acceleration M3 MacOS" FIXED in 126; bug 1892457 10-bit AV1 on M3 FIXED 127). https://bugzilla.mozilla.org/show_bug.cgi?id=1871796

### Window occlusion / App Nap
- Occlusion: nsCocoaWindow::DispatchOcclusionEvent (widget/cocoa/nsCocoaWindow.mm ~L7238) uses NSWindowOcclusionStateVisible; fully occluded -> OcclusionStateChanged -> CanonicalBrowsingContext::RecomputeAppWindowVisibility deactivates window and pauses compositor (nsIWidget::PauseOrResumeCompositor). No pref; env var MOZ_WINDOW_OCCLUSION (anything but "1" disables). Key/main non-fullscreen windows are never treated as occluded (bug 2033230, workaround for Bartender-style tools). Fullscreen windows are treated as not occluded.
- App Nap: Firefox DISABLES App Nap for the parent process at startup. toolkit/xre/MacApplicationDelegate.mm DisableAppNap() registers NSAppSleepDisabled=YES in NSUserDefaults; called from nsAppRunner.cpp L4557. Reason in source comment: child processes are not napped, so a napped parent gets queued IPC. Bug 931651 "Investigate support for Mavericks' App Nap" is REOPENED (https://bugzilla.mozilla.org/show_bug.cgi?id=931651). IMPLICATION for a fork: macOS never naps the Firefox parent; an idle chrome-side timer/animation keeps the parent at full wake-ups.

### Tab unloading
- browser.tabs.unloadOnLowMemory = true on mac/win (firefox.js L1229); only on low memory, not battery. browser.tabs.min_inactive_duration_before_unload = 600000 ms (L1236). browser.lowMemoryPollingIntervalMS=10000. browser.tabs.unloadTabInContextMenu=true. No time-based idle auto-discard by default.
- Process model: dom.ipc.processCount.webIsolated=4 (all.js L1878), dom.ipc.processPrelaunch.fission.number=3, dom.ipc.processPriorityManager.enabled=true; backgroundUsesEcoQoS=false (Windows-only block). Process priority on mac: unverified.

### Q1 additions: QoS / background process priority (macOS)
- threads.use_low_power.enabled = true on macOS (Nightly-only elsewhere) (SPL ~L19841): "set threads to low-power mode when in the background".
- threads.lower_mainthread_priority_in_background.enabled = true on macOS (SPL ~L19853): when process priority is background, the main thread is put in background QoS. Works with dom.ipc.processPriorityManager.enabled=true (SPL ~L3754), so background-tab content processes get lower priority (E-cores on Apple Silicon). Bug 1960734 (FIXED 139, component Agent) disabled these only for automation (Marionette) because background-tab content processes stalled under CPU load. https://bugzilla.mozilla.org/show_bug.cgi?id=1960734
- Bug 1678083 (dup) "Investigate Using Low Power Cores for Some Threads on Apple Silicon" is where the E-core idea started (2020). https://bugzilla.mozilla.org/show_bug.cgi?id=1678083
- macOS 26 Tahoe: bug 1995638 (FIXED 146) made nsThreads default to QOS_CLASS_USER_INITIATED because Tahoe deschedules threads without QoS and Firefox felt sluggish; bug 1996052 (FIXED 146) limited it to macOS 26+; bug 1999447 (NEW) proposes reverting for 26.1+ because Apple fixed a video-decode thread-priority bug in 26.1. https://bugzilla.mozilla.org/show_bug.cgi?id=1995638 , /1996052 , /1999447. Lesson: a fork's chrome JS/native threads should not assume default QoS is E-core friendly; user-initiated QoS on all nsThreads costs power.
- Video low-power mode (macOS system "Core Animation video low power mode"): NativeLayerRootCA::CheckVideoLowPower (gfx/layers/NativeLayerCA.mm ~L518) requires 1 video, topmost layer AVSampleBufferDisplayLayer, 420 YpCbCr, black opaque full-screen backing layer, FULLSCREEN window. Telemetry glean gfx.macos_video_low_power (labels notvideo, lowpower, failmultiplevideo, failwindowed, failoverlaid, failbacking, failmacosversion, failpref, failsurface, failenqueue). So: windowed video never gets the macOS video low power path in Gecko. Sampled every gfx.core-animation.low-power-telemetry-frames=600 frames.

## Q2. Low Power Mode / thermal / battery awareness

- Gecko has NO code reacting to macOS Low Power Mode or NSProcessInfo thermalState. Grepped widget/cocoa/nsCocoaWindow.mm, nsCocoaUtils.mm, nsAppShell.mm, toolkit/xre/*.mm, nsAppRunner.cpp, gfx/layers/NativeLayerCA.mm, StaticPrefList.yaml for lowPowerMode/thermalState/NSActivity: zero hits (only NSProcessInfo processIdentifier/systemUptime). Bugzilla full-text of summaries: only bug 1749952 (NEW, Widget: Cocoa) "Trackpad scrolling jumps in macOS Low power mode with ProMotion" mentions LPM, and it is a bug report, not a feature. https://bugzilla.mozilla.org/show_bug.cgi?id=1749952 . Confidence: high for these files, "unverified" for whole tree (no code search available).
- Battery vs AC: Battery Status API exists. dom.battery.enabled=true (SPL ~L2696). dom/webidl BatteryManager.webidl is [ChromeOnly, Exposed=Window]: `charging`, `chargingTime`, `dischargingTime`, `level`, plus onchargingchange/onlevelchange events. So privileged chrome JS can do `window.navigator.getBattery()` (nav getBattery chrome-only; web content cannot). macOS backend: hal/cocoa/CocoaBattery.cpp uses IOKit IOPowerSources (IOPSKeys, IOPSGetTimeRemainingEstimate). Bug 696045 "Battery API: MacOS X backend" FIXED (mozilla18). Web exposure was removed for privacy (bug 751016 security review; bug 1047119). Exact removal version: unverified. LPM/thermal not exposed by it.
- "Power saver" mode in Firefox: none shipped. Bug 1351755 "Provide Slight/Light/Low power/Battery saving/Battery saver mode option" is NEW; a 2023-06-26 comment from Florian says "we are preparing an experiment" (text truncated in my read) but nothing shipped as of last change 2025-03-11. https://bugzilla.mozilla.org/show_bug.cgi?id=1351755 . Related: 1499259 (dup), 1812109.
- Other power-ish prefs: gl.allow-high-power=true (WebGL prefers high-power GPU; irrelevant on single-GPU Apple Silicon), webgl.power-preference-override=0.
- Practical for the fork: implement LPM/thermal awareness in privileged JS or a small native shim (NSProcessInfo.lowPowerModeEnabled + NSProcessInfoPowerStateDidChange notification; thermalState + NSProcessInfoThermalStateDidChange) that flips prefs like layout.frame_rate, dom.timeout.* and animation toggles. No upstream hook exists; this is new code. Battery vs AC can be had today from navigator.getBattery() in chrome.

## Q3. Measuring power on macOS / catching idle loops

### Firefox Profiler power tracks
- Profiler "power" feature exists (tools/profiler/core/platform.cpp, MACRO(20,"power",Power,...) in mozglue/baseprofiler/public/BaseProfilerState.h). Help string differs by platform: arm64 macOS = "Sample per process power use"; amd64 macOS = whole-system power. So on Apple Silicon the numbers are PER PROCESS, not system.
- Apple Silicon implementation: tools/profiler/core/PowerCounters-mac-arm64.cpp calls task_info(mach_task_self(), TASK_POWER_INFO_V2) and reports task_energy (nanojoules, converted to picowatt-hour). One counter "Process Power" per process, sampled with each profiler sample. No sudo needed. It is Apple's per-task energy accounting (a model, not a rail measurement; CPU+GPU attribution is Apple's estimate). Intel Mac path uses RAPL (needs different setup).
- Enable: (a) profiler popup preset "Power" (Mozilla perf blog 2022-10-27: https://blog.mozilla.org/performance/2022/10/27/whats-new-with-the-firefox-profiler-q3-2022/ ; says power capture available on Windows 11 and Apple Silicon; shows power tracks with tooltip of instant power and energy over selection); (b) about:profiling -> Features -> "Power Use" ("power"); (c) about:processes "profile" button enables ["default","ipcmessages","power"] (aboutProcesses.js ~L1841; bug 1777564 FIXED 104). Gecko Profiler samples at 1 ms by default and its own samples cause wakeups; docs warn it distorts what it measures: https://firefox-source-docs.mozilla.org/performance/power_profiling_overview.html . Use interval 5-10 ms for power runs (my suggestion, not from docs).
- pref devtools.performance.recording.power.external-url (all.js L665) is for importing external power tracks into a recording.
- Docs gap: official docs are Intel-era (powermetrics page dated 2015: https://firefox-source-docs.mozilla.org/performance/powermetrics.html). FOSDEM 2024 slides "Firefox Power Profiling: a powerful visualization of web sustainability" (https://archive.fosdem.org/2024/events/attachments/fosdem-2024-2716-firefox-power-profiling-a-powerful-visualization-of-web-sustainability/slides/22726/FOSDEM_2024_-_Firefox_Power_Profiling_a_powerfu_Q635bzv.pdf) mention an undocumented per-process API on Apple Silicon; content could not be read by my fetcher (unverified details).

### about:processes
- Columns are only Name, Memory (resident), CPU total (%) and Kill (toolkit/components/aboutprocesses/content/aboutProcesses.html; aboutProcesses.js). NO energy/power/wakeup column. It shows "almost idle / fully idle" labels from cpuCycleCount deltas, per tab too. Use it to spot a busy parent (chrome) process and which tab/extension is busy, then use the profile button.

### powermetrics (local `powermetrics -h` on macOS 27.0.1 arm64 confirms flags)
- Typical: `sudo powermetrics --samplers tasks,cpu_power,gpu_power,ane_power,thermal,battery --show-process-coalition --show-process-energy --show-process-gpu -i 5000 -n 6`
- Flags available: --show-process-coalition (groups parent+children, a Dock-launched app shows under its bundle id; Terminal-launched under com.apple.Terminal, so launch the fork from Dock/`open` not from a shell), --show-process-energy ("per-process energy impact number"), --show-process-gpu, --show-process-qos(-tiers), --show-process-io, --show-process-ipc, --show-process-amp. Samplers: tasks, battery, cpu_power, thermal, gpu_power, ane_power (+ all/default groups).
- Docs: tasks columns ms/s CPU, Deadlines (<2ms, 2-5ms), Wakeups (Intr, Pkg idle). Idle target: parent process interrupt wakeups near single digits per second, deadlines near zero. (Mozilla docs warn Activity Monitor "Energy Impact" is a hybrid proxy and should not be used for comparisons.)
- WindowServer and kernel_task should be included in totals: chrome-side redraw shows up as WindowServer + GPU time, not only in the Firefox coalition.
- `mach power` wrapper (powermetrics + rapl) is Intel-era; rapl does not exist on Apple Silicon (unverified for mach power on arm64).

### Catching a chrome refresh-driver loop or animation at idle
- nsRefreshDriver (layout/base/nsRefreshDriver.cpp) only keeps its vsync timer running while GetReasonsToTick() != None. Reasons: HasObservers (rAF, style/layout flush observers, animations), HasImageAnimations (animated GIF/APNG not throttled), HasPendingRenderingSteps, RootNeedsMoreTicksForUserInput. With none, StopTimer() unregisters from vsync, so a truly idle window has no ticks. Also layout.keep_ticking_after_load_ms=1000 and first-contentful-paint extra ticking limited to 4 s.
- Diagnostic 1: Gecko Profiler marker `RefreshDriverTick` (category Graphics) carries text "Tick reasons: HasObservers (<observer descriptions with flush types>) ..." when the thread is profiled with markers. Enable it on the PARENT process (chrome refresh driver) via about:profiling with "main process" thread/Markers, or profile with preset "Graphics"/"Power". A steady train of RefreshDriverTick markers on the Parent Process main thread while idle = chrome animation/rAF loop. The description lists which observers are registered. (nsRefreshDriver.cpp ~L2380)
- Diagnostic 2: MOZ_LOG=nsRefreshDriver:5 logs timer add/remove, "ticking drivers..." and inactive timer scheduling (LOG macro, nsRefreshDriver.cpp L110, L356).
- Diagnostic 3: layout.frame_rate=N clamps tick rate (e.g. 10) to check whether power tracks with ticks; -1 default = vsync (120 Hz on ProMotion).
- Diagnostic 4: WebRender debug prefs (gfxPlatform.cpp L511-545 builds flags from prefs gfx.webrender.debug.*): .profiler (on-screen frame/GPU timings), .picture-caching, .picture-borders, .render-targets, .texture-cache, .show-overdraw, .gpu-time-queries, .window-visibility, .highlight-backdrop-filters (marks backdrop-filter regions: directly useful for the vibrancy-vs-CSS question), .highlight-painted-layers, .blob.paint-flashing. The old nglayout.debug.paint_flashing(_chrome) prefs (bugs 895003, 899701, 2013) are NOT in current SPL/all.js/firefox.js (searchfox: only gfx.webrender.debug.blob.paint-flashing remains). unverified whether a chrome-only repaint flash still works; DevTools "Paint flashing" in the Browser Toolbox is the likely replacement (unverified).
- Diagnostic 5 (inference, unsourced): Browser Toolbox (devtools) can inspect chrome DOM and the Animations panel; CSS animations with `animation-iteration-count: infinite` on hidden elements keep compositor animations alive.
- Telemetry that already exists to compare against: glean power.total_thread_wakeups and power.wakeups_per_process_type (platform.cpp ~L8107).

## Q4. Native macOS materials in Gecko chrome

Source files: widget/cocoa/VibrancyManager.mm, widget/cocoa/nsCocoaWindow.mm, widget/cocoa/nsNativeThemeCocoa.mm, browser/themes/shared/browser-shared.css, widget/cocoa/nsLookAndFeel.mm (all on firefox main, fetched 2026-10-12).

### CSS appearance -> NSVisualEffectView material
- Only TWO chrome appearances create window-backed vibrancy regions (nsNativeThemeCocoa::ThemeGeometryTypeForWidget, ~L1759):
  - `-moz-default-appearance: -moz-sidebar` -> VibrancyType::Sidebar -> NSVisualEffectMaterialSidebar (VibrancyManager.mm L34-40). Blend mode behind-window when widget.macos.sidebar-blend-mode.behind-window=true (default true), else within-window.
  - `-moz-default-appearance: -moz-window-titlebar` -> VibrancyType::Titlebar -> NSVisualEffectMaterialTitlebar. Blend mode behind-window only if widget.macos.titlebar-blend-mode.behind-window=true (default FALSE), else within-window.
  - `-moz-window-button-box` -> eThemeGeometryTypeWindowButtons (traffic lights placement, not a material).
  Both widgets paint nothing themselves (WidgetInfo returns Nothing()); the region is reported to nsCocoaWindow::UpdateVibrancy and the OS draws NSVisualEffectViews underneath the CoreAnimation layers. Colors: system color keywords `-moz-sidebar`, `-moz-sidebarborder`, `-moz-sidebartext`.
- Where the browser uses it: browser/themes/shared/browser-shared.css L338-362: under `@media (-moz-platform: macos) and (-moz-native-theme)`, `:root[customtitlebar]:not([lwtheme], [macOSNativeFullscreen]) #navigator-toolbox::after { appearance: -moz-window-titlebar }` with transparent toolbox background; skipped when a lightweight theme is applied and in native fullscreen. Bugs referenced: 1949528, 1476281. Sidebar (history/bookmarks sidebar, places organizer) uses `-moz-sidebar` color/appearance (browser/themes/osx/places/organizer.css L75).
- Menus and tooltips are NOT CSS-driven: nsCocoaWindow wraps popup windows in a native effect view (nsCocoaWindow.mm ~L8415-8450 newEffectViewWrapperForStyle): WindowShadow::Menu -> NSVisualEffectMaterialMenu (macOS < 26) or NSGlassEffectView (macOS 26+, cornerRadius 12 on Tahoe, 6 before); WindowShadow::Tooltip -> NSVisualEffectMaterialToolTip, corner radius 5 on macOS 26 ("GoldenGate") else 0; blendingMode BehindWindow, state Active. Panels/None get a plain NSView.
- Other prefs: widget.macos.native-popovers=false (NSPopover for `type="arrow"` panels; the source comment in StaticPrefList.yaml literally says "Someone like Zen browser will use this pref by default"), widget.macos.native-context-menus=true, widget.macos.native-anchored-menus=true, widget.macos.allow-native-select=true, widget.macos.window-transforms.disabled=false, widget.macos.shift-by-menubar-on-fullscreen=2.
- No other NSVisualEffect materials (HUD, popover, underWindowBackground, hudWindow, contentBackground...) are reachable from CSS today. A fork wanting those has to add a new StyleAppearance value + VibrancyType + material mapping in widget/cocoa/VibrancyManager.mm (small C++ patch, but it widens the diff vs upstream and needs Rust style crate change for a new appearance keyword; alternatively reuse `-moz-sidebar` regions as the material for any chrome area, since regions are just rects).

### Liquid Glass / macOS 26
- NSGlassEffectView IS used by Gecko, but only for menu popups: bug 1992894 "Use macOS Tahoe style in menupopups" FIXED in Firefox 145 (pushed 2025-10-07): "In macOS Tahoe, menus use a glass effect instead of vibrancy" + larger metrics. https://bugzilla.mozilla.org/show_bug.cgi?id=1992894
- Related Tahoe fixes: 1988774 window corner radius (FIXED 145), 1993747 radius round 2 (NEW), 1993148 popup border radius (FIXED 145), 1992898 native-styled controls sizing (FIXED 145), 1989223 Liquid Glass app icon (FIXED 146), 1997245 dark icon (FIXED 147), 1992611 window buttons too small (dup). Meta: 1971185 "[meta] macOS 26 Tahoe issues tracking bug" (NEW). https://bugzilla.mozilla.org/show_bug.cgi?id=1971185
- No bug found for glass on the toolbar, sidebar, titlebar or whole window (searched "glass", "Liquid Glass", "NSGlassEffectView" in Bugzilla summaries). Sidebar/titlebar still use NSVisualEffectView materials. So full-window Liquid Glass chrome = unverified/unsupported upstream; would be fork work (NSGlassEffectView needs macOS 26 SDK at build time; CPython issue reported some Liquid Glass behaviours need app compiled against the 26 SDK: https://github.com/python/cpython/issues/139404 , unverified for Gecko).
- Apple Developer Forums report of NSGlassEffectView background not updating on macOS 26.2 (https://developer.apple.com/forums/thread/810314) is a risk flag for any glass-behind-window design.

### Cost: native vibrancy vs CSS backdrop-filter
- Native vibrancy: the blur is computed by WindowServer on the GPU, not by Gecko (Markus Stange, bug 1420638 comment 2, 2017-11-26: "the blurring work that the window server has to do happens on the GPU, not on the CPU"; "no evidence" of non-trivial power impact but "we haven't gathered any numbers"). Bug 1420638 "mac os default theme vibrancy may increase power usage" is still NEW with no measurements. https://bugzilla.mozilla.org/show_bug.cgi?id=1420638
- Known pitfall fixed in Firefox 70: WindowServer recomputed vibrancy blur on every composite of the whole window, even when only page pixels changed. Fix: composite into multiple framebuffers so vibrant layers do not refresh when page content scrolls (bug 1574586, FIXED mozilla70). https://bugzilla.mozilla.org/show_bug.cgi?id=1574586 . Design rule for the fork: keep vibrant regions as separate, static native layers; do not put animated content over them.
- CSS backdrop-filter: layout.css.backdrop-filter.enabled=true (SPL L11032), software path is expensive. Meta bug 1888024 "[meta] [project] Fix performance issues with backdrop-filter" (NEW, 2024-03-27). Bug 1995379 (2025-10-20, New Tab team): backdrop-filter blur(10px) on cards gave ~3x memory vs baseline and 98% Renderer CPU in profiler, visible lag on an M4 MacBook Pro or 4K display, worse at high resolution because the backdrop re-renders per element; they dropped the feature. https://bugzilla.mozilla.org/show_bug.cgi?id=1995379 . Bug 1628046 (FIXED): backdrop-filter over-invalidates and defeats picture caching when backdrop root is the whole page. Bug 2051662 (NEW): PDF viewer scrolling choppy due to backdrop-filter. Mozilla guidance (implied): avoid backdrop-filter on large/many/scrolling elements in chrome; debug with gfx.webrender.debug.highlight-backdrop-filters and gfx.webrender.debug.picture-caching.
- Recommendation supported by evidence: use native NSVisualEffectView regions (sidebar/titlebar/menu) for blur; no CSS backdrop-filter in chrome. No published numeric power comparison of native vibrancy vs backdrop-filter exists that I could find (unverified).

### Reduced transparency / motion in chrome CSS
- prefers-reduced-transparency: macOS value from NSWorkspace.accessibilityDisplayShouldReduceTransparency (widget/cocoa/nsLookAndFeel.mm ~L501, IntID::PrefersReducedTransparency). The media feature is ALWAYS enabled in chrome/UA sheets; for web content it is behind layout.css.prefers-reduced-transparency.enabled=false (servo/components/style/queries/feature_expression.rs ~L323; SPL L11253). So chrome CSS can write `@media (prefers-reduced-transparency)` today. Native NSVisualEffectViews respond to the system setting on their own.
- prefers-reduced-motion: NSWorkspace.accessibilityDisplayShouldReduceMotion (nsLookAndFeel.mm ~L497, IntID::PrefersReducedMotion); override with pref ui.prefersReducedMotion (LookAndFeel int pref; exact existence in this tree unverified). Enabled for all content (shipped since Firefox 63). Chrome CSS can use `@media (prefers-reduced-motion)`.
- Also relevant: `-moz-platform: macos` and `-moz-native-theme` media features gate the vibrancy rules; resistFingerprinting spoofs reduced-transparency for web content only (RFPTargets.inc).

### Is a thin UI layer over upstream Firefox credible?
- Mechanisms that work on stock Firefox without a fork: userChrome.css (appearance only), fx-autoconfig by MrOtherGuy (loads privileged userChrome.js scripts via autoconfig; install = copy into the Firefox app dir) https://github.com/MrOtherGuy/fx-autoconfig , Sine mod manager https://github.com/CosmoCreeper/Sine (built on fx-autoconfig, loads userChrome/userContent and Zen-format mods), Natsumi (Zen-like theme/features; "Natsumi Append" requires fx-autoconfig; installable through Sine) https://awesome.ecosyste.ms/projects/github.com%2Fgreeeen-dev%2Fnatsumi-browser . Sidebery-type extensions can't touch chrome internals.
- Limits: autoconfig runs privileged JS after startup, so chrome code can add UI and prefs, but cannot change C++ (widget/cocoa, vibrancy types, QoS, DisableAppNap) or built-in about: pages without patching omni.ja. Rebranding/auto-update/signing and packaged defaults (policies.json, autoconfig.js) require shipping your own app bundle anyway; on macOS modifying the .app breaks the code signature, so a distributable build still needs re-signing/notarization (standard, unverified for this specific path).
- Practical verdict: "Zen UI as privileged JS + CSS over a stock-engine build" is credible for look/feel and features (workspaces via tab groups + vertical tabs). It is NOT a path to better battery by itself, because the power items in Q1-Q4 live in native code and prefs. A hybrid is cheapest: upstream-built binary (or tiny patch set) + omni.ja/autoconfig layer for UI.
- Existing projects doing it: Natsumi + Sine (stock Firefox via fx-autoconfig); Floorp (own fork, own workspaces, see Q6); Zen itself is a full fork (patches + surfer). unverified: current star counts / maintainership of Natsumi and Sine.

## Q6. How Gecko forks track Firefox (4-week train is now a 2-week train)

### Release train facts (critical)
- Firefox moved from 4-week to 2-week major releases starting with Firefox 155 (2026-09-01, moved up from 09-15). 154 (2026-08-18) was the last 4-week release. Schedule: 156 = 09-15, 157 = 09-29, 158 = 10-13, 159 = 10-27 ... 164 = 2027-01-26. Sources: Mozilla SUMO blog https://blog.mozilla.org/sumo/2026/08/19/firefox-new-release-cadence-and-what-to-expect/ ("dot releases may still happen when needed, albeit not as often"); Register/Linuxiac/Neowin coverage via search (https://linuxiac.com/firefox-to-test-a-two-week-release-cycle-starting-in-september/ ) which frame it as an "experiment" (Sylvestre Ledru); ESR is unaffected per those reports (SUMO post is silent on ESR/experiment end, unverified there).
- Dot releases are still weekly in practice (product-details.mozilla.org/1.0/firefox.json): e.g. 152.0 (06-16) then .1 06-18, .2 06-23, .3 06-25, .4 06-30, .5 07-07, .6 07-14; 153.0 07-21, .1 07-28, .3 08-04, .4 08-11; 154.0 08-18, .1 08-25; 155.0 09-01, .1 09-04; 156.0 09-15, .1 09-22; 157.0 09-29, .1 10-06. So a fork that wants to ship every security build must produce a release roughly every week, about 40+ per year, plus a major rebase every 2 weeks since 155.
- Current pace of work: 150 -> 157 in 23 weeks (7 majors) is 3.3 weeks per major, and 4-8 majors in the next ~3 months.

### Patch strategy and tooling
- Zen: patch queue plus new-file tree, driven by npm scripts wrapping the surfer CLI (@zen-browser/surfer). `surfer download` fetches Firefox source into ./engine (version pinned in surfer.json: version.version=157.0.1, candidate=158.0 for RC/twilight builds), `surfer import` applies src/ over engine, `surfer export` writes changes back as patches, `npm run sync` = scripts/update_ff.py (bumps surfer.json, re-imports; `sync:rc` for release candidates, `sync:l10n`), `surfer update`, `surfer reset`, `use-moz-src` (mach), `npm run ffprefs` (Rust tool in tools/ffprefs that generates pref overrides), `npm run ci`. Repo composition on dev: 263 .patch files under src/, plus src/zen (1,135 files, ~28 MB incl. svg assets and JS) = new code that lives alongside the engine; src/external-patches has 13 files (cherry-picked/backported upstream patches); src/browser 397 files, src/layout 32, src/toolkit 40, src/widget 15, src/gfx 4, src/dom 12. Source: package.json scripts, GitHub git/trees API on dev (2026-10-12).
- LibreWolf: prefs-first. Repo holds patches/ (many are sed-patches, e.g. patches/sed-patches/disable-pocket.patch), settings/ (librewolf.cfg, policies), theming. Patch dev tool scripts/git-patchtree.sh (apply patch tree, edit, commit, diff against "initial"); Makefile targets: dir, bootstrap, build, package, run; CI makes source tarballs (source-release.yaml) published to S3/CDN; bsys6 repo builds binaries for Win/Linux/macOS; downstream packagers (Arch, Gentoo, Alpine) consume the tarball. Upstreaming: patches rewritten against mozilla-unified (hg) for Bugzilla. https://codeberg.org/librewolf/source
- Floorp: full-tree repo wrapping a mach build with its own Deno task runner (`feles-build`, phases before-mach and after-mach), moz.build glue, UI in `floorp/browser/...` and `browser-features/`, native/macos-app-shim, floorp-runtime.lock.json (pinned runtime; meaning unverified). Floorp 12 is built around "Noraneko" (UI as separate TS/Vite project injected into Firefox). https://github.com/Floorp-Projects/Floorp
- Waterfox: full source tree with Mozilla platform code, Waterfox code, branding and packaging in one repo. https://github.com/BrowserWorks/waterfox

### Lessons for a small diff (derived from the above; mark as my inference where no source)
- Put new UI in new files/dirs (Zen src/zen, Floorp browser-features) and keep edits to existing Firefox files as small, separate patches. Zen's 263 patches show how fast the patch count grows even for a "UI fork"; LibreWolf stays small by being prefs, policies and sed patches.
- Express changes as prefs/policies/autoconfig wherever possible (LibreWolf, Zen ffprefs tool). Prefs from Q1/Q3 (layout.frame_rate, dom.timeout.*, widget.macos.*) cost zero rebase effort.
- Automate the bump: version in one file (surfer.json), one script to download, import, build, with CI to open the PR. Zen mean 2.2 days with this setup.
- Cadence reality: 2-week majors (155+) plus weekly dot releases means rebase conflicts show up every 2 weeks. Patches touching widget/cocoa/nsCocoaWindow.mm and browser CSS will conflict most (Tahoe work is active: bugs 1971185, 1992894, 1993747). Keep C++ patches in leaf files (new VibrancyType, new helper files) rather than inline edits.
- Alternative (inference): follow ESR (Waterfox model) to cut rebase frequency to ~1 per year, but you lose upstream native features of 136-157 (vertical tabs etc. exist in ESR 153 only if ESR 153 contains them; ESR 153 shipped features up to 153, unverified) and ESR gets security fixes only via backports. ESR 153 existence is from the FreeBSD port note; unverified on mozilla.org.

## Q7. Battery / energy evidence on Apple Silicon (2024-2026)

Bottom line: there is NO rigorous published test that compares Zen, Firefox, Safari and Chrome on Apple Silicon for video playback or browsing, and Mozilla published no Apple Silicon power numbers in 2024-2026. Most "Safari wins on battery" pieces are vendor-marketing or lack methodology. Plan to measure yourself (Q3).

Independent tests found
- Matt Birchler (Birchtree), 2025-06-22, M4 Pro MacBook Pro, macOS Tahoe beta, beta browsers, 5-hour web browsing run, twice per browser, scripted (script on GitHub). Remaining battery after 5 h: Safari 61%, Arc 67%, Zen 68% (higher = better). Author: "less scientific than the last time", "not a scientific test bench"; Safari "consistently and inexplicably the hardest" on battery. So Zen (Gecko) used about 7 points less battery than Safari over 5 h in this one test; Firefox was not tested. https://birchtree.me/blog/seriously-use-the-browser-you-like-dont-worry-about-battery/
- Birchtree, 2024-09-14, M2 Pro 14" MBP, Sonoma, Chrome 128 vs Safari 17.6, 20-min loop (10-min YouTube video + Mastodon + news + Google Docs typing) x9 = 3 h per run, 6 runs per browser, 30% brightness. Safari 18.67% drain per 3 h (16.1 h projected), Chrome 17.33% (17.3 h). Chrome ~9% less battery, wins 5 of 6 pairs, large run-to-run variance (one pair Safari 10% less, another Chrome 14% less). No Firefox. https://birchtree.me/blog/everyone-says-chrome-devastates-mac-battery-life-but-does-it-i-tested-for-36-hours-to-find-out/ ; discussed at https://mjtsai.com/blog/2024/09/17/does-google-chrome-still-devastate-mac-battery-life/
- Alex Yumashev (jitbit), updated 2025-05-31, MacBook M3 Pro: Speedometer 3.0: Chrome 37.7, Brave 37.6, Safari 18.2 37.6, Firefox 134.0.2 34.8, Zen 1.7.3b 31.6. So Zen scored ~9% below its Firefox base and ~16% below Chrome. Battery NOT measured; memory chart only (helper-process undercount corrected). https://www.jitbit.com/alexblog/zen-review-benchmark/ . Speedometer is a speed proxy; lower score often means more CPU time per task.
- Mihnea Radulescu "BrowserBench" (AppleScript-driven multi-tab browsing, open source), as quoted by SupaSidebar: Brave avg 743 mW vs Safari 1,356 mW (peak 8.3 W vs 10.5 W). Hardware/date not stated in the secondary source; Firefox not quoted. Treat as unverified.
- Apple spec (Safari only, vendor): M4 14" MBP up to 16 h wireless web / 24 h video (1080p Apple TV app); M4 Pro/Max 14" 14 h / 22 h; M3 14" 15 h / 22 h. Tom's Guide real-world M4 Pro 14" web test ~20 h (via SupaSidebar). Secondary-source, unverified.
- SupaSidebar posts (supasidebar.com, 2026) say Zen/Firefox trail Safari on streaming battery and "within 20 to 30 percent" for mixed browsing; the author sells SupaSidebar, gives no test of his own. Do not rely on it. https://supasidebar.com/blog/zen-browser-vs-safari-mac-2026 ; https://supasidebar.com/blog/best-browser-mac-battery-life-2026
- Reddit r/macapps "[Part 3, final] Browser energy efficiency benchmarks" (2023-04-15, author FedaykinLanfear_8423) measured raw power for Chrome, Arc, Safari, Firefox, Brave, Orion, Edge, SigmaOS, Opera, 20-min sessions x3 on one browsing pattern. Numbers are in images; I could not read them (reddit blocked). Outside the 2024-2026 window anyway. unverified.
