# Milestone 5 release research, 2026-10-13

What Origin needs for signed updates and a first public release. Read from the tree on 2026-10-13: Firefox 157.0.1 in `engine/`, surfer in `node_modules/@zen-browser/surfer/dist/`, Zen's workflows in the local `upstream` branch. Nothing was built or run. Anything not read from source is marked unverified.

Paths starting with `engine/` are relative to `/Users/mrm/Zen-Origin`.

## Findings that change the plan

1. The updater is off. `configs/macos/mozconfig:10-13` has `--disable-updater` with a `ponytail:` note. Remove it and set the options below in the same commit.
2. `surfer.json` has no `updateHostname`. surfer then writes `MOZ_APPUPDATE_HOST=localhost:7648 # This should not resolve` into the mozconfig (`node_modules/@zen-browser/surfer/dist/constants/mozconfig.js:53`). Without the key the updater would poll a dead address. Set it before enabling the updater.
3. Zen's `dist/update/browser/.../update.xml` from the stock build still points at `github.com/zen-browser/desktop` (stock build predates our `surfer.json`). A rebuilt Origin points at `Sowyu/Origin` because `surfer.json` has `github.repo`.
4. The MAR must be made from the signed `.app`, after `scripts/sign-app`. The code signature files are part of the bundle, so a MAR from the unsigned app would install a broken signature. Zen's CI does the same: it signs the app in the object dir and then runs `JUST_MAR=1 npm run package` (`macos-universal-release-build.yml`, steps "Sign .app" then "Package for mar").
5. The signed MAR has a new hash and size. The `update.xml` must be written (or patched) after signing. Zen patches it in `scripts/mar_sign.sh` (`update_manifests`).
6. Elevated updates need `--enable-mac-elevated-updates-with-generic-certs`. See "Configure options".

## MAR signing and verification

### How verification works

- The updater verifies each MAR against certificates compiled into `updater` as byte arrays. `engine/toolkit/mozapps/update/updater/gen_cert_header.py` turns each `.der` file into a header.
- Which `.der` files go in depends on the update channel. `engine/toolkit/mozapps/update/updater/moz.build:94-131`: channels `beta`, `release` and `esr` use `release_primary.der` and `release_secondary.der`. Nightly channels use `nightly_aurora_level3_*`. Everything else uses `dep1.der` and `dep2.der`. `xpcshellCertificate.der` is for tests.
- surfer sets `--enable-update-channel=<brand>` and Origin's brand is `release` (`surfer.json`, `constants/mozconfig.js:44`), so the `release_*` pair is the one that matters.
- `engine/toolkit/mozapps/update/updater/archivereader.cpp:78-95`: the updater tries the primary certificate, and if that fails it tries the secondary. Each try is one certificate against the MAR's signatures.
- `engine/modules/libmar/verify/mar_verify.c:281` succeeds only if every signature in the MAR verified and the key count equals the verified count. A MAR therefore carries exactly one signature, made by the primary or the secondary key. A MAR signed with both fails.
- Algorithm: RSA with SHA-384. `engine/modules/libmar/sign/mar_sign.c:92` signs with `SEC_OID_PKCS1_SHA384_WITH_RSA_ENCRYPTION`. On macOS the updater verifies with the Security framework (`engine/modules/libmar/verify/MacVerifyCrypto.cpp:115,150-159`), using the certificate only to get its public key. Zen uses RSA 4096 and that works in their builds.
- The cert's validity dates are not read by `SecCertificateCopyPublicKey`, so an expired cert does not matter to the updater (unverified). Zen's script uses 2000-01-01 to 9999-12-31 anyway.
- The updater also checks the MAR's channel ID against `ACCEPTED_MAR_CHANNEL_IDS` and refuses a MAR with an older product version (`archivereader.cpp:125-168`). The MAR is stamped with `mar -H <channel> -V <version>` by `engine/tools/update-packaging/make_full_update.sh:44`.

### Configure options

- `--enable-unverified-updates` turns verification off (`engine/build/moz.configure/update-programs.configure:47`). Never set it. Leave it unset so `MOZ_VERIFY_MAR_SIGNATURE` stays on (lines 52-73).
- `MAR_CHANNEL_ID` and `ACCEPTED_MAR_CHANNEL_IDS` (same file, lines 146-160). surfer sets both to the brand (`constants/mozconfig.js:47-50`), so both are `release`.
- `--enable-mac-elevated-updates-with-generic-certs` (same file, lines 78-137). Without it, the privileged helpers' `SMAuthorizedClients` and `SMPrivilegedExecutables` requirements demand Mozilla's team id `9V5K9TP787` (line 91). Origin is signed by team `8Q677AYRU7`, so the requirement would not match and any update that needs elevation would fail. With the option, the requirement is `identifier "<id>" and anchor apple generic`. Add `ac_add_options --enable-mac-elevated-updates-with-generic-certs` to `configs/macos/mozconfig`. Whether a normal drag-installed copy owned by the admin user ever needs elevation is unverified. The option is cheap, so add it anyway.
- `--enable-nss-mar` (lines 166-185) makes macOS use NSS instead of the system crypto. Leave it off. Zen does not set it.
- `MOZ_APPUPDATE_HOST` comes from the mozconfig through `engine/build/moz.build:95-97`. The default there is `aus5.mozilla.org`, so a build that forgets the variable would talk to Mozilla.

### Create the key and certificate

`scripts/mar_sign.sh` is Zen's script and already does most of this.

1. `bash scripts/mar_sign.sh -g` runs `openssl genrsa 4096`, a self-signed cert (`CN=MAR Signing`, valid 2000 to 9999), and writes `build/signing/{private_key.pem,cert.pem,public_key.der}`. It also writes base64 copies under `build/signing/env/` for CI secrets.
2. `bash scripts/mar_sign.sh -i` copies `public_key.der` over the five `.der` files in `engine/toolkit/mozapps/update/updater/`.
3. Rebuild so the updater embeds the new certificate.

Problems for Origin:

- `build-origin` runs `git -C engine checkout -- .` first (`scripts/build-origin:11`), which restores Mozilla's certificates. Run `-i` after that reset, before `build`. Otherwise the updater verifies against Mozilla's key and every Origin MAR fails.
- The script writes the private key to `build/signing/private_key.pem`, a base64 copy under `env/`, and `password.txt` in the NSS dir. Origin should not use `-g` or `-s` as they are. 
- Zen puts one certificate in all five slots. Origin should generate two keys and use A for `release_primary.der` and B for `release_secondary.der` (and A for the rest). The updater accepts a MAR signed by either, so B is the rotation path if A is lost or leaks (`archivereader.cpp:89-92`). Where B lives is for the user to decide, because the spec says to ask before a signing key leaves this Mac.

### Keep the private key in a keychain

CandyWrapper's pattern (`../CandyWrapper/docs/release.md`, "Signing on the build Mac") stores the Sparkle seed as a generic password in `~/Library/Keychains/candywrapper-release.keychain-db`, unlocked through `security -i` with the password read from another login-keychain item. Reuse that keychain or make `origin-release.keychain-db` the same way.

`signmar` only reads keys from an NSS database, and NSS cannot use a macOS keychain item. So the key has to be extractable and the keychain holds it as a secret:

1. Store the PEM once: `security add-generic-password -a release -s io.github.sowyu.origin.mar-key-a -w "$(cat private_key.pem)" <keychain>`. Then delete the PEM from disk. Whether a multi-line PEM survives `-w` is unverified. Base64 on one line avoids the question.
2. At release time, unlock the keychain as CandyWrapper does, read the item with `security find-generic-password -w`, and pipe it into `openssl pkcs12 -export` reading the key from stdin and the public cert from `public_key.der` or `cert.pem`.
3. Create a throwaway NSS DB in a `mktemp -d` folder with mode 700: `certutil -N -d <dir> --empty-password` (unverified flag), then `pk12util -i - ` is not possible from stdin, so write the `.p12` into the same temp folder, import it, delete it.
4. Sign: `signmar -d <dir> -n mar_sig -s in.mar out.mar`, then verify with `signmar -d <dir> -n mar_sig -v out.mar` (as `scripts/mar_sign.sh:200-207` does).
5. `rm -rf` the temp folder in a `trap` on exit. For a stricter setup, make the folder on a RAM disk (`hdiutil attach -nomount ram://...`, unverified size and flags) so the key never touches the SSD.

`certutil`, `pk12util` and `signmar` exist in the stock build at `engine/obj-aarch64-apple-darwin/dist/bin/`, so no Linux build is needed. Zen's CI takes `signmar` from its Linux build (`linux-bin-x86_64/signmar`). Copy the three tools out of the object dir into `../Zen-Origin-research/tools` so a later object-dir cleanup does not remove them (unverified that they run standalone; they load NSS libraries from the same `dist/bin`).

An alternative without an extractable key: a small Swift tool that signs with a non-exportable key in the keychain. The MAR signature is a plain RSA PKCS#1 SHA-384 signature over a hash of the MAR (`mar_sign.c`), so it is possible, but it means reimplementing the MAR signature block layout. Not worth it for a single maintainer (unverified estimate).

The key is still readable by any process of this user, the same limit the CandyWrapper doc records. The off-machine backup question from that doc applies here too: losing key A with no key B in the shipped updater strands every installed copy until a manual reinstall.

## The update feed

### URL

- The update URL is not a pref. Firefox reads `[AppUpdate] URL` from `application.ini`, built from `engine/build/application.ini.in:53-55`, and `UpdateService` returns `Services.appinfo.updateURL` (`engine/toolkit/mozapps/update/UpdateService.sys.mjs:5491-5517`). An enterprise policy `AppUpdateURL` overrides it (same function).
- Mozilla's template is `https://@MOZ_APPUPDATE_HOST@/update/6/%PRODUCT%/%VERSION%/%BUILD_ID%/%BUILD_TARGET%/%LOCALE%/%CHANNEL%/%OS_VERSION%/%SYSTEM_CAPABILITIES%/%DISTRIBUTION%/%DISTRIBUTION_VERSION%/update.xml`. surfer rewrites it to `https://@MOZ_APPUPDATE_HOST@/updates/browser/%BUILD_TARGET%/%CHANNEL%/update.xml` (`commands/patches/branding-patch.js:285-291`, and it shows in the working tree `engine/build/application.ini.in:55`).
- Placeholders are replaced in `engine/toolkit/modules/UpdateUtils.sys.mjs:60-112` and each value is URL-encoded. The ones available are `PRODUCT`, `VERSION`, `BUILD_ID`, `BUILD_TARGET`, `OS_VERSION`, `LOCALE`, `CHANNEL`, `PLATFORM_VERSION`, `SYSTEM_CAPABILITIES`, `DISTRIBUTION` and `DISTRIBUTION_VERSION`. Zen's patch makes `%VERSION%` the Firefox version (`AppConstants.ZEN_FIREFOX_VERSION`, `src/toolkit/modules/UpdateUtils-sys-mjs.patch`), not the Zen version.
- `%BUILD_TARGET%` is `Services.appinfo.OS + "_" + ABI`, and ABI is `XPCOMABI` on macOS (`UpdateUtils.sys.mjs:1073-1090`). For an arm64 build that should be `Darwin_aarch64-gcc3` (matches surfer's `ausPlatformsMap.macosArm`; the runtime value is unverified, check with `about:support` or the update log once a build runs).
- A foreground check appends `?force=1`, and a pin policy appends `pin=`. Static hosting ignores query strings.
- The channel is `release`, so the full feed path is `/updates/browser/Darwin_aarch64-gcc3/release/update.xml`.
- Using only `%BUILD_TARGET%` and `%CHANNEL%` means the feed has no per-version logic: the same file always names the latest release, and the updater decides if it is newer. That suits static hosting.

### update.xml

surfer already writes it (`commands/updates/browser.js:60-160`). For the stock build it produced `dist/update/browser/Darwin_aarch64-gcc3/release/update.xml`:

```xml
<?xml version="1.0"?>
<updates>
  <update type="minor" displayVersion="1.23.2b" appVersion="1.23.2b" platformVersion="157.0.1" buildID="20261012144832">
    <patch type="complete" URL="https://github.com/.../releases/download/1.23.2b/macos.mar" hashFunction="sha512" hashValue="..." size="93602322"/>
  </update>
</updates>
```

- `appVersion` is what the updater compares with the running version. `displayVersion` is shown to the user. `buildID` must be the new build's ID from `platform.ini`.
- surfer writes one file per `ausPlatformsMap` entry, which for macOS is `Darwin_aarch64-gcc3` plus four Intel targets (`browser.js:19-40,119-124`). Origin is arm64 only, so publish only the `Darwin_aarch64-gcc3` directory.
- The MAR URL is `https://github.com/<repo>/releases/download/<displayVersion>/macos.mar`. The tag is therefore the bare display version with no `v` (`browser.js:75-79`), and the asset name is hardcoded to `macos.mar` for Darwin (`browser.js:46-48`). `surfer.json`'s `archives` list (`macos-aarch64.mar`) is not read there. Use `macos.mar` for the asset name, or write the XML with a tiny script of our own (about 10 lines) and name the asset `origin-<ver>-arm64.mar`.
- The hash and size in surfer's file are for the unsigned MAR. After signing, patch both (as `mar_sign.sh` `update_manifests` does) or generate the XML after signing.
- The MAR URL redirects to GitHub's object storage. Zen ships this way, so the updater follows redirects (unverified for the arm64 Origin build, but identical code).
- Version choice: `appVersion` is a Mozilla version string like `1.23.2b`. If Origin ever ships two builds on top of one Zen release, it needs a version that sorts above `1.23.2b`. How Mozilla's comparator orders `1.23.2b.1` against `1.23.2b` is unverified. The simplest scheme is to bump only with Zen releases.

### Serve it from GitHub Pages

- Zen does this: `zen-browser/updates-server` holds `updates/<...>/update.xml` and CI commits to it (`build.yml` job `release`, steps "Checkout updates repository", "Copy update manifests", "Commit"). `spec.md` says the same.
- GitHub Pages serves project sites at `https://<owner>.github.io/<repo>/`. For repo `Sowyu/Origin` that is `https://sowyu.github.io/Origin/`, a path prefix. `MOZ_APPUPDATE_HOST` is pasted textually into `https://@MOZ_APPUPDATE_HOST@/updates/...`, so `sowyu.github.io/Origin` produces a valid URL. That works as long as nothing parses the value as a host. The only user seen is `application.ini.in:55`, but a full search of `engine/` was not allowed here. Unverified.
- A cleaner choice is a separate repo `Sowyu/updates` so the host is `sowyu.github.io/updates`, or a repo named `sowyu.github.io` so the host is `sowyu.github.io` with no prefix. A separate repo also keeps feed commits out of Origin's history. Either way `surfer.json` needs `"updateHostname": "<that value>"`.
- Pages deploys from a branch or an Actions run. A branch-based deploy takes some seconds to minutes (unverified). Publish the MAR release first, then the feed, so the feed never names a missing file. CandyWrapper's script does the same ordering for its appcast.
- The feed is public and unauthenticated, as is the MAR. The signature protects the content, so the hosting does not need to be trusted.

## Release artifacts

### DMG

- `npm run package` copies the DMG to `dist/` (`dist/zen-1.23.2b.en-US.mac.dmg` for the stock build, 124,799,190 bytes). The brand sets the name; check it comes out as an Origin name after the rebrand.
- Zen signs the DMG, notarizes it and staples it (`macos-universal-release-build.yml`, step "Sign .dmg"). Origin has no Developer ID, so none of that applies. Sign the app with `scripts/sign-app` (Apple Development, team `8Q677AYRU7`) before making the DMG. `scripts/sign-app` signs inside out with Firefox's hardened-runtime entitlements from `engine/security/mac/hardenedruntime/production`.
- Zen builds the DMG itself with `mozbuild.action.make_dmg` after signing (same step). Origin needs the same order: package, sign the app in the object dir, make the DMG from the signed app. `scripts/build-origin` does not do the signing yet (it ends at `package`). Whether `npm run package` accepts an already signed app is unverified. A rerun of `mozbuild.action.make_dmg` as Zen does is the known path.

### MAR

- Complete MAR: `engine/tools/update-packaging/make_full_update.sh <outdir> <app>` with `MOZ_PRODUCT_VERSION`, `MAR_CHANNEL_ID`, `ACCEPTED_MAR_CHANNEL_IDS` and `MAR` set; surfer's `createMarFile` (`package.js:127-154`) sets them. It writes `output.mar`. Stock Zen's was 93,602,322 bytes against a 124,799,190 byte DMG.
- Partial MARs: `engine/tools/update-packaging/make_incremental_update.sh` makes a patch between two builds, and there is a Zucchini variant (`make_incremental_zucchini.py`). They need the previous release's complete app or MAR, a separate `<patch type="partial">` element per source build in the XML, and one more signed file. surfer's own comment says partials "might be nice" and leaves them out (`browser.js`, TODO in the patch object). Zen ships none.
- Recommendation: complete MARs only for the first releases. A complete MAR is about 94 MB, and a user on a week old build downloads that once per update. Partials would cut this, but the saving is untested and the cost is a second input, a second signature step and a rule for which builds get a partial. Add them if download size becomes a complaint (unverified that it will). This is a guess.
- With weekly releases from Firefox's cadence (`spec.md`), the feed names only the latest build, so someone several releases behind still gets a complete MAR. That is fine.

### SHA-256 sums

- `shasum -a 256 *.dmg *.mar > SHA256SUMS` and upload it with the assets. The spec asks for sums. The update itself uses SHA-512 from the XML, so the sums file is for people who download the DMG.
- GitHub also shows a SHA-256 digest for uploaded release assets (returned as `digest` in the assets API) (unverified, the API was not called). Do not rely on it as the only source.

### GitHub Releases through the REST API

CandyWrapper's `../CandyWrapper/scripts/release` (lines 220-275) already does this with `git credential fill` and urllib, so copy its approach instead of writing a new one:

1. Read the token: `git credential fill` with `protocol=https`, `host=github.com`. Never print it.
2. `POST https://api.github.com/repos/Sowyu/Origin/releases` with `tag_name`, `target_commitish`, `name`, `body` (release notes, no AI attribution) and `prerelease`. Headers `Authorization: Bearer <token>`, `Accept: application/vnd.github+json`.
3. If the tag exists, `GET /repos/Sowyu/Origin/releases/tags/<tag>`, delete the old asset (`DELETE /releases/assets/<id>`) and upload again, which makes a rerun safe.
4. Upload each file to `POST https://uploads.github.com/repos/Sowyu/Origin/releases/<id>/assets?name=<file>` with the file as the body and its content type.
5. Download one asset back and check its SHA-256 before publishing the feed.

The tag must match the URL in `update.xml` (bare `1.23.2b` by surfer's rule). The token needs write access to the repo's contents. It lacks the `workflow` scope (`CLAUDE.md`), which only matters for pushing workflow files.

## What Zen's CI does

From the `upstream` branch (`git show upstream:.github/workflows/<file>`), for the same steps:

- `build.yml` (848 lines) is the entry point, run by hand or on a schedule through `twilight-release-schedule.yml`. Inputs include `create_release`, `update_version` and `update_branch`. Jobs: build data, check-release, Windows, Linux, macOS, AppImage, source tarball, then `release`.
- macOS is three stages when PGO is on: `mac-step-1` instrumented build, `mac-step-2` profile run (`macos-profile-build.yml`), `mac-step-3` build with the profile. Each builds x86_64 and aarch64 in a matrix.
- `macos-release-build.yml` runs on `blacksmith-8vcpu-ubuntu-2404`, a paid third-party runner, and cross-compiles from Linux with cctools and `libdmg` fetched by `./mach artifact toolchain`, cached under `~/mac-cross`. It writes the mozconfig-driven build through `.github/workflows/src/release-build.sh`, which calls `bash ./scripts/mar_sign.sh -i` before `npm run build` (so the certificate import happens right before building, as proposed above).
- API keys (`ZEN_SAFEBROWSING_API_KEY`, `ZEN_MOZILLA_API_KEY`, `ZEN_GOOGLE_LOCATION_SERVICE_API_KEY`) are written to `~/.zen-keys` for the build and deleted after. Origin ships without them unless the user decides otherwise (not checked what features need them).
- `macos-universal-release-build.yml` runs on `macos-26`: builds the host `mar` tool from `tools/update-packaging`, unpacks both DMGs, merges them with `unify.py`, signs the app with `mach macos-sign` using a Developer ID `.p12` and a provisioning profile from secrets, builds the DMG with `make_dmg`, converts it to UDZO, signs it, notarizes it with `xcrun notarytool` and staples it. It then runs `JUST_MAR=true npm run package` against the unified app to make `macos.mar` and uploads `dist/update` as `macos_update_manifest`.
- The `release` job (runs on `blacksmith-2vcpu-ubuntu-2404`, environment `Deploy-Release`) downloads all artifacts, runs `scripts/mar_sign.sh -s` with `signmar` from the Linux build and the key from secrets (`ZEN_SIGNING_PRIVATE_KEY_PEM_BASE64`, `ZEN_SIGNING_CERT_PEM_BASE64`, `ZEN_MAR_SIGNING_PASSWORD`), runs `scripts/mar_verify.sh`, copies the manifests into `zen-browser/updates-server`, commits them, builds release notes and publishes with `softprops/action-gh-release`. The release holds the MARs and DMGs and Windows installers. There are no SHA-256 sums.
- `mar_verify.sh` is worth keeping. It checks that each MAR exists, is not empty, verifies against `build/signing/public_key.der` and matches the manifest's hash and size, and it stops the release on the first failure.

What Origin drops: Windows, Linux, universal merge, Developer ID signing, notarization, provisioning profile, the second repo for secrets. What Origin keeps: the sign, verify, manifest and publish order.

### Free runners

The spec asks to try Zen's recipe on free GitHub runners before asking about paid ones. Zen builds on Linux runners and uses a macOS runner only for the unify, sign and notarize step. A native arm64 macOS runner would avoid the cross toolchain. Whether a public repo's free macOS arm64 runner can finish a Firefox build is unverified: this Mac needs 1,404 s for `mach build` with 10 cores and peaked at 14 GB of memory (`docs/benchmarks.md`), and free hosted runners have fewer cores, less memory, and a six hour job limit (unverified numbers). Signing needs the Apple Development identity from this Mac's login keychain, which should not go to CI; so a hosted runner can only build, and signing and the release must run here.

## Suggested order for milestone 5

1. Decide the feed host (`sowyu.github.io/Origin`, a separate repo, or a custom domain) and set `updateHostname` in `surfer.json`.
2. Generate keys A and B, store A in the release keychain, ask the user where B goes.
3. Remove `--disable-updater`, add `--enable-mac-elevated-updates-with-generic-certs`, make `build-origin` run the certificate import after its engine reset.
4. Build, sign the app, make the complete MAR from the signed app, sign the MAR, write the XML, make the DMG, write `SHA256SUMS`.
5. Test an update end to end on this Mac from a build with an older version to a newer one, against a local server first (`app.update` uses the policy `AppUpdateURL` for a test build, unverified), then against the real feed.
6. Script the release (copy `../CandyWrapper/scripts/release`), then the weekly rebase job.

Open questions for the user:

- Where does key B live, given the rule that no signing key leaves this Mac?
- Which feed host?
- Is the final name settled (affects bundle name, DMG name, tag)?
