# Lazy loading candidates, 2026-10-13

Research only, no builds and no measurements. Every memory number is a guess and marked unverified. I read the working tree as of today, with the cut features already deleted.

## 1. How the startup load works

- src/browser/base/content/zen-assets.inc.xhtml:8-25 links 17 stylesheets into every browser.xhtml. Line 37 loads src/zen/common/ZenPreloadedScripts.js.
- src/zen/common/ZenPreloadedScripts.js:9-23 imports 10 modules with `{ global: "current" }`. Each window gets its own copy of each module and of everything those modules import statically. That is the real cost, because one more window means one more copy of all of it.
- Source size of what every window loads this way is about 610 KB: ZenSpaceManager 109,025 B, ZenViewSplitter 80,011, ZenDragAndDrop.js 75,586 (loaded at line 53), ZenFolders 73,303, ZenGradientGenerator 68,503, ZenUIManager 59,551, ZenKeyboardShortcuts 45,285, ZenPinnedTabManager 36,307, ZenCompactMode 33,232, plus about 40 KB of smaller files (ZenSpacesSwipe, ZenSpaceAddSwipe, ZenEmojiPicker, ZenMenubar and others).
- src/zen/ZenComponents.manifest registers only nsBrowserGlue. src/zen/sessionstore/SessionComponents.manifest:6 and :9 register ZenWindowSync.init and uninit. Nothing else Zen-specific runs at app-startup.
- The XPCOM components in src/zen/compact-mode/components.conf (mouse tracker) and src/zen/drag-and-drop/components.conf are reached through lazy service getters (ZenCompactMode.mjs:55-57, ZenDragAndDrop.js:76-80), so they already load on first use.

## 2. Already lazy, nothing to do

- src/zen/vendor/motion.min.mjs (140,697 B) sits behind a lazy getter, but see candidate 1: the getter fires at startup.
- src/zen/common/emojis/ZenEmojisData.min.mjs (185,912 B) loads only in the `#emojis` getter at ZenEmojiPicker.mjs:88-100. The first use is the popupshowing handler at ZenEmojiPicker.mjs:176-184, and `#clearEmojis` (line 139) deletes the data again when the panel hides. No change needed.
- ZenEmojiPicker.mjs itself is 9,890 B and builds nothing until the panel opens. Leave it.
- The custom elements zen-folder, zen-workspace, zen-workspace-creation and zen-workspace-icons (ZenPreloadedScripts.js:28-51) load on first creation. ZenEssentialsPromo.mjs loads through defineESModuleGetters at ZenDragAndDrop.js:111-117.
- ZenWindowSync.sys.mjs (56,378 B) and ZenSessionManager.sys.mjs (37,253 B) load in the main process. Window sync is a kept feature and session data is needed at startup (ZenSpaceManager.mjs:717), so there is nothing to defer.

## 3. Candidates, ranked by likely saving per change

### 1. Motion library loads in every window at the first tab

- File and size: src/zen/vendor/motion.min.mjs, 140,697 B, Motion v13.2.0. It is a UMD script, so ZenUIManager.mjs:36-43 runs `loadSubScript(url, window)` and every window holds its own compiled copy.
- How it loads now: the lazy getter `gZenUIManager.motion` (ZenUIManager.mjs:36-43).
- What triggers it at startup: `_canAnimateItemOpen` (ZenUIManager.mjs:1059-1070) tests `!gZenUIManager.motion` before the cheap checks `_hasLoadedDOM` and `gZenStartup.isReady`. `animateItemOpen` calls it from Tabbrowser-sys-mjs.patch:376 for every tab created, including session restore. `animateItemClose` (ZenUIManager.mjs:1160-1164) has the same pattern.
- First real use: the tab open and close animations (ZenUIManager.mjs:1112, 1137, 1172), the new-tab button popup (256, 265), tab rename (1727), workspace switching (ZenSpaceManager.mjs:2180, 2225, 2291), compact mode (ZenCompactMode.mjs:468, 517), split view and the space creation form.
- Smallest change, step A: in `_canAnimateItemOpen` and `animateItemClose`, move `!gZenUIManager.motion` to the end of the condition. Restored tabs then hit `!gZenStartup.isReady` first and skip the load. This is a two-line move.
- Step B, bigger: the tab open, close and rename animations (four call sites, ZenUIManager.mjs:1112-1180 and 1727) are plain opacity, transform, margin and filter keyframes, which native `element.animate()` does. Then Motion loads only for workspace switches, compact mode and split view. Easing "easeOut" becomes "ease-out", and `.finished` replaces the thenable.
- Risk: step A is near zero. Step B changes how animations look and finish, so check by eye and with the harness.
- Memory: unverified, guess 0.5 to 1.5 MB per window for the compiled script and its objects. Step A alone loses most of the gain once the user opens a first tab, so step B is the one that keeps it off for good.

### 2. Keyboard shortcuts rewrite and save the file in every window

- File and size: src/zen/kbs/ZenKeyboardShortcuts.mjs, 45,285 B. Lines 974-1318 are migrations that only run when the saved version is old.
- How it loads now: ZenPreloadedScripts.js:13, then `beforeInit()` from ZenStartup.mjs:24 and `init()` at ZenKeyboardShortcuts.mjs:1345-1357.
- The startup work: `init()` reads zen-keyboard-shortcuts.json, then `_applyShortcuts()` (lines 1465-1487) rebuilds the whole zenKeyset in every open window, then `_saveShortcuts()` (lines 1529-1535) writes the JSON file again. With n windows, opening one more window does n keyset rebuilds and a disk write, even when nothing changed.
- First real use of the data: the keys must exist when the user presses a shortcut, so the keyset itself cannot wait. The settings page (zen-settings.js:7, 240) and the command palette hint (ZenUBActionsProvider.sys.mjs:389) use the manager later.
- Smallest change: in `init()`, skip `_saveShortcuts()` when the loaded file exists, `versioner.isVersionUpToDate()` is true and `fixedKeyboardShortcuts` added or dropped nothing. Apply the shortcuts only to this window on its first load, instead of looping over `nsZenMultiWindowFeature.browsers`. A bigger step moves `migrate()` and `zenGetDefaultShortcuts()` into a lazy module, since they only matter for a first run or a version bump.
- Risk: medium. `_applyShortcuts` also serves the settings page, so keep the all-windows loop in `triggerShortcutRebuild` and `setShortcut`. Check that a new window still gets the user's custom keys.
- Memory: unverified, guess 100 to 300 KB per window if the migration half moves out. The write and the rebuild are startup time and disk work, not memory. Measure window open time with 1, 4 and 8 windows.

### 3. Urlbar providers register at window startup

- Files and sizes: src/zen/urlbar/ZenUBActionsProvider.sys.mjs 19,360 B, ZenUBGlobalActions.sys.mjs 8,875, ZenUBSidebarProvider.sys.mjs 7,405, ZenUBResultsLearner.sys.mjs 3,017. Together 38,657 B.
- How it loads now: ZenUIManager.mjs:214-223 `_initOmnibox()` runs at window init (called at line 66) and calls `registerZenUrlbarProviders()` from ZenUBProvider.sys.mjs:15-25. That function walks `Object.values(lazy)`, which fires the lazy getters, so both provider modules and their imports load at once. These are shared modules, so the cost is once per process in the main process, not once per window.
- First real use: the first query typed in the urlbar (the providers' `isActive` runs per query, for example ZenUBSidebarProvider.sys.mjs:37).
- Smallest change: in `_initOmnibox`, replace the direct call with a one-shot focus listener on `gURLBar` (`{ once: true }`) that calls `registerZenUrlbarProviders()`. Typing needs focus and `registerProvider` is synchronous, so the first query already sees the providers.
- Risk: low to medium. A query started without focus (a keyboard search shortcut path, or an automated test) would miss the providers for that one query. Check focus on `cmd_openLocation` and on search mode entry.
- Memory: unverified, guess 100 to 300 KB in the main process once, plus less startup work in the first window.

### 4. Split view loads in every window and the tabbrowser calls it on hot paths

- File and size: src/zen/split-view/ZenViewSplitter.mjs, 80,011 B, plus zen-split-view.css 5,939 B and zen-split-group.inc.css 4,795 B.
- How it loads now: ZenPreloadedScripts.js:16, which creates `window.gZenViewSplitter` at ZenViewSplitter.mjs:2593. The constructor waits for DOMContentLoaded and then `init()` (lines 89-130) adds TabClose, TabSelect and TabBrowserDiscarded listeners and a dragover listener on the tab box.
- First real use: a user splits tabs (zen-sets.js:31-76, the tab context menu, a drag onto the page edge at ZenDragAndDrop.js:1089 and 1266).
- Why it is hard: the tabbrowser patches call it all the time. `splitViewBrowsers` (Tabbrowser-sys-mjs.patch:9) is a getter used all over the tab code, and `_maybeRemoveFakeBrowser` and `_canDrop` run on every tab move (Tabbrowser-sys-mjs.patch:1093-1094). SessionStore calls `storeDataForSessionStore` and `restoreDataFromSessionStore` (SessionStore-sys-mjs.patch:267, 326). A plain lazy getter would load the module at once.
- Smallest change: define a stub `window.gZenViewSplitter` in ZenPreloadedScripts.js with `splitViewBrowsers` (returns `[]`), `_maybeRemoveFakeBrowser` (no-op), `_canDrop`, `waitingForSplitTab`, `storeDataForSessionStore` (returns `[]`) and `restoreDataFromSessionStore` (loads the real module only when the saved data is not empty). Add a `load()` that imports the real module and calls `init()` by hand, since the DOMContentLoaded hook has already fired. Every public entry (the commands in zen-sets.js, the context menu items, the drop handlers) calls `load()` first.
- Risk: high. There are many call sites in tabbrowser and sync code (ZenSpacesSyncApplier.sys.mjs:776-847 and ZenWindowSync.sys.mjs:1511-1699 use it directly), and the context menu item is added in `init()`. It needs the full split view tests. It also touches Zen UI code that the user may replace in a rewrite (CLAUDE.md hard rule), so ask first.
- Memory: unverified, guess 200 to 500 KB per window, counting the 80 KB source, stylesheet rules and listeners.

### 5. Theme picker: the whole picker UI is set up at startup

- File and size: src/zen/spaces/ZenGradientGenerator.mjs, 68,503 B, static import at ZenSpaceManager.mjs:7. Panel markup src/browser/base/content/zen-panels/theme-picker.inc, 12,510 B and 85 elements, parsed into every window. Stylesheet src/zen/spaces/zen-gradient-generator.css, 9,958 B.
- How it loads now: `new nsZenThemePicker()` at ZenSpaceManager.mjs:793. The constructor (ZenGradientGenerator.mjs:98-179) wires the panel's popupshowing, popuphidden and command listeners, builds 16 texture dots (`initTextureInput`, line 351), and hooks up the color pages, scheme buttons, custom color input and opacity slider. It also adds a toolbar context menu item.
- First real use: `openThemePicker` (line 221) from `cmd_zenOpenZenThemePicker` (zen-sets.js:60), and `openThemePickerForWorkspace` (line 1944) from the space creation form.
- Why only part of it can wait: the gradient math (`getGradientForWorkspace`, line 2071, and `onWorkspaceChange`, line 1527) paints every window's background and is needed at startup. But `onWorkspaceChange` also touches picker DOM (`sliderWavePath` at line 1627, `customColorList` at line 1739).
- Smallest change: move the UI half of the constructor (lines 126-163: panel listeners, `initPredefinedColors`, `initColorPages`, `initSchemeButtons`, `initTextureInput`, `initCustomColorInput`) into one `#ensureUI()` called from `openThemePicker` and `openThemePickerForWorkspace`, and guard the two DOM touches in `onWorkspaceChange`. The further step splits the picker half of the file (about lines 212-1230 plus 1886-1960) into its own module imported by `#ensureUI()`, and loads zen-gradient-generator.css by appending a `<link>` there and waiting for its load event before `PanelMultiView.openPopup`.
- Risk: medium. `promiseInitialized` (resolved around line 148) is the guard `onWorkspaceChange` uses for other windows (line 1534). Keep it resolved without the UI. The user said not to put deep work into Zen UI code that a rewrite would replace, so ask before the file split.
- Memory: unverified, guess 100 to 300 KB per window for the setup, and 300 to 500 KB with the file split and the sheet.

### 6. ZenUIMigration import on every launch

- File and size: src/zen/common/sys/ZenUIMigration.sys.mjs, 5,443 B, main process.
- How it loads now: BrowserGlue-sys-mjs.patch:27 calls `lazy.gZenUIMigration.init(...)` at every startup. `init` re-runs `_migrate`, `#restoreDownloadsButton` and rewrites the version pref.
- Smallest change: in the BrowserGlue patch, read `zen.ui.migration.version` and `zen.library.migrated-downloads-button` first and skip touching `lazy.gZenUIMigration` when both say done. It still has to run for a new profile.
- Risk: low. Memory: unverified, tens of KB in the main process once.

### Not worth doing

- ZenDragAndDrop.js (75,586 B). `new window.ZenDragAndDrop(this)` runs when `<tabs>` connects (tabs-js.patch:25) and it subclasses the built-in `TabDragAndDrop`, which receives the tab strip's events. Lazy loading would need a proxy for every drag event.
- ZenFolders.mjs (73,303 B). Hot paths call it: `handleTabPin` and `handleTabUnpin` (Tabbrowser-sys-mjs.patch:119, 139), `canDropElement` (line 1001), `cancelPopupTimer` on space switch (ZenSpaceManager.mjs:1795, ZenUIManager.mjs:1782), and SessionStore (SessionStore-sys-mjs.patch:275, 325). It would load at once.
- ZenSpacesSwipe.mjs and ZenSpaceAddSwipe.mjs (8,425 B and 7,806 B). `zen.workspaces.swipe-actions` defaults to true (prefs/zen/workspaces.yaml:17) and the constructor registers the gesture listeners (ZenSpaceManager.mjs:190-196).
- ZenCompactMode.mjs (33,232 B) and ZenPinnedTabManager.mjs (36,307 B). Both are used from many places and have little code that runs only on demand.
- ZenSiteDataPanel.sys.mjs (22,905 B). The constructor builds the visible identity button and the copy URL button (ZenSiteDataPanel.sys.mjs:23-80), so it is needed at startup.

## 4. Stylesheets in every window that only style panels or popups

All sizes are source bytes. Parsed sheets are shared, so the saving per window is only the style data each document builds from them (unverified, guess tens of KB per window for all of these together). The whole group is small, so do these last.

- src/zen/spaces/zen-gradient-generator.css, 9,958 B, theme picker panel only. Load it from the picker (candidate 5). This is the only one worth a change.
- src/zen/spaces/create-workspace-form.css, 4,828 B, pulled into zen-workspaces.css by `%include` at line 427. Only the space creation form uses it. Moving it out needs its own link and a load before the form opens.
- src/zen/split-view/zen-split-view.css 5,939 B and zen-split-group.inc.css 4,795 B, active only with a split. Tie them to candidate 4.
- src/zen/folders/zen-folders.css lines 196-300, the tabs search popup (`#zen-folder-tabs-popup`), about 2.5 KB. The rest styles folders in the tab strip, which is needed.
- src/zen/common/styles/zen-popup.css, 10,547 B, mixes panel and menu rules with root and toast rules. It imports zen-panels/bookmarks.css 1,352 B, dialog.css 837 B and print.css 256 B (lines 6-8). Those three are tiny, so leave them.
- src/zen/common/styles/zen-panel-ui.css, 2,502 B, holds rules for `menupopup` and `panel[type="arrow"]`, so it applies to every popup. Leave it.
- src/zen/common/styles/zen-single-components.css, 17,535 B, mixes the emoji picker (lines 57-185), the site data panel (lines 290-630) and swipe add-space (lines 689-801) with always-on rules. Splitting it adds diff against upstream for little gain.

The panel markup in the popupset (src/browser/base/content/zen-popupset.inc.xhtml includes theme-picker.inc with 85 elements, popups.inc 41, site-data.inc 31, emojis-picker.inc 13, folders-search.inc 7) is parsed into every window. That is 177 elements. The listeners are wired in the constructors listed above, so I would only touch the theme picker (candidate 5).

## 5. How to check the guesses

1. Open about:memory with 1 window and again with 4 windows, click "Measure", and compare the `window-objects` and `js-main-runtime/realms` entries for `chrome://browser/content/browser.xhtml`, especially `scripts/` and `gc-heap`. The per-window difference is what these changes can remove.
2. Make change 1 step A first. It is two lines, and its before and after numbers show what one 140 KB script costs per window, which calibrates the rest.
3. Measure window open time with 1, 4 and 8 windows before and after change 2.
